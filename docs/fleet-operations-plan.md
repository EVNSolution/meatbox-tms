# 다차량 주문 배송 관제 구현 계획

## 결정 요약

이번 변경은 주문을 이미 접수한 뒤부터 배송이 끝날 때까지를 시연한다. 운영 뷰어의 세 업무는 주문 배차 지도, 다차량 배송 목록, 선택 배송 관제로 나눈다. 지도는 주문 관리에서만 사용하며, 배송 목록과 배송 관제에서는 한 배송지를 여러 패널에 반복하지 않는다.

현재 차량 130대, 배송지 4,523곳과 9,090박스는 화면 구조와 밀도를 검토하기 위한 임시 예시 데이터이며 확정 요구사항이 아니다. 이후 정제한 실제 데이터의 차량, 배송지와 박스 합계를 기준으로 사용한다. 추가 실제 주문 좌표, 권역 경계, 차량 배차 알고리즘과 외부 알림 채널은 후속 연동 작업에서 공급한다. 이번 구현은 원본 시뮬레이션의 계산과 상태를 그대로 두고 게이트웨이 래퍼에서 다차량 표본, 배송팁, 고객 알림과 고객용 ETA 시간 범위를 보강한다.

## 범위와 우선순위

- 사용자 최신 결정이 기존의 지도 없는 운영 화면과 ETA 정책보다 우선한다.
- 주문 관리는 운영 뷰어에서 지도를 쓰는 유일한 페이지다.
- 차량 사고와 정차 지연을 직접 발생시키는 버튼은 전체 시나리오 화면에서 제거한다. 원본 시뮬레이션 계산 함수와 사건 처리 알고리즘은 수정하지 않는다.
- `workspaces/jiin-ui/`와 `workspaces/sanghyun-scenario/`는 보존 원본이다. 원본 바이트와 `docs/source-snapshots.json` 검증을 유지한다.
- 구현은 `apps/combined/`, 게이트웨이 래퍼와 테스트에 한정한다. 주문 지도는 고객 뷰어와 같은 로컬 MapLibre·OFM 자산과 이미 등록된 route data만 사용한다. 새 지도 좌표, 권역, 배차 결과, 외부 푸시 또는 알림톡 발송을 만들지 않는다.
- 시연 화면의 문구에는 파일, 모듈, WebSocket 명령명과 같은 개발 구조를 노출하지 않는다.
- 시간 기반 자동 진행은 [수동 시나리오 전환 계획](manual-scenarios-plan.md)의 여섯 프리셋으로 교체한다. 로컬 검토 뒤 별도 릴리스 SHA와 인증된 운영 화면으로 배포 결과를 확인한다.

## 요구사항 근거와 시간 의미

`/Users/jiin/Downloads/미트박스 TMS 역할 요약.docx`는 고객 ETA의 기본 표현 예시를 `13:00 ~ 14:00 도착 예정`과 같은 시간 범위로 제시한다. 같은 문서의 `실제 도착 시점 대비 ±15분 이내 80% 이상`은 장기적인 예측 정확도 목표다. 이는 한 고객에게 보여 주는 시간 범위나 지연 알림 임계값과 다른 개념이다.

이번 작업에서 고객 화면은 정확 ETA를 중심으로 앞뒤 30분의 시간대를 보여 준다. 운영 화면은 정확 ETA를 계속 보여 준다. 고객 지연 알림은 현재 정확 ETA가 해당 고객에게 마지막으로 약속한 기준보다 늦게 30분을 **초과**할 때 발생한다. 정확히 30분 늦어진 경우에는 알리지 않는다. 이 임계값은 Word 문서에서 가져온 수치가 아니라 이번 사용자 결정이다.

## 시나리오와 데이터 규모

아래 수량은 현재 UI 회귀에 사용하는 고정 fixture일 뿐 향후 실데이터 계약이나 수량 상한이 아니다.

| 구분 | 차량 | 배송지 | 박스 | 성격 |
|---|---:|---:|---:|---|
| 실제 시연 V1 | 1대 | 8곳 | 60박스 | 기존 원본 시뮬레이션과 상호작용 |
| 다차량 표본 V2부터 V130 | 129대 | 4,515곳 | 9,030박스 | 차량별 35곳, 배송지별 2박스 |
| 전체 운영 표본 | 130대 | 4,523곳 | 9,090박스 | 목록과 선택 UI 밀도 검토 |

현재 fixture의 원시 스냅샷은 `fleet.vehicles` 130대와 합성 배송지 4,515곳을 가진다. 어댑터는 기존 실시간 배송지 8곳을 유지하고 전체 조회용 `fleetDeliveries`에 결합한다. 후속 실데이터에서는 차량 수, 배송지 수와 박스 합계를 수신 데이터에서 읽고 이 fixture의 개수와 ID 규칙을 요구하지 않는다.

`adapted.fleetVehicles`의 차량 항목은 `id`, `plate`, `driver`, `region`, `live`, `status`, `planned.stops`, `planned.boxes`, `capacityBoxes`를 제공한다. `adapted.fleetDeliveries`의 배송 항목은 `id`, `vehicleId`, `vehicle`, `name`, `address`, `boxes`, `ordered`, `status`, `customerStatus`, `preciseTimeText`, `customerWindowText`, `customerWindowStart`, `customerWindowEnd`, `tip`, `notices`를 제공한다. 내장 `vehicle`은 `id`, `plate`, `driver`, `region`, `live`를 가진다.

합성 차량 ID는 `V2`부터 `V130`까지다. 합성 배송지 ID는 `V{2..130}-S{1..35}`이며 각 차량에 2박스 배송지 35곳을 배정한다. 계획 합계는 차량당 70박스지만 `capacityBoxes`는 `null`로 두어 적재량 제한으로 확정하지 않는다. 합성 배송지는 `ordered: true`, `status: "pending"`, 고객 상태 `paid / 결제 완료`, 주소 `위치 데이터 대기`를 사용한다. 확인되지 않은 좌표, ETA와 시각은 `null` 또는 `미확인`으로 두며, 가짜 알림 발송 시각을 만들지 않는다. 실시간 차량 판별은 `delivery.vehicle.live === true`를 우선하고 호환 경계에서만 `vehicleId === "V1"`을 사용한다.

`tip`은 값이 없으면 `null`, 있으면 `{ body, author, updatedAt }`이다. `notices`는 `{ id, stopId, time, title, body, kind, channel, status, author? }` 배열이다. 고객 알림 채널과 상태는 시연 내부 기록임을 분명히 하며 실제 외부 발송 성공을 뜻하지 않는다.

알림 이력은 정차지마다 최근 50건을 먼저 보존하고 초과한 오래된 항목을 제거한다. 그 다음 전체 알림을 최근 1,000건으로 제한하고 전역에서 가장 오래된 항목부터 제거한다. 따라서 화면의 고객 알림은 보존 범위 안의 최근 기록이며 전체 영구 이력이 아니다. 알림 ID는 이력 정리와 초기화에 관계없이 같은 서버 실행 동안 단조 증가한다. 초기화는 알림 내용을 비우지만 다음 ID를 되돌리지 않는다. 어댑터는 스냅샷의 알림을 한 번 순회해 `stopId`별로 묶고 4,523개 배송에 재사용한다.

## 주문 관리

주문 관리는 주문이 서비스에 접수된 상태에서 시작한다. 페이지 본문은 넓은 지도 캔버스를 중심으로 구성한다. 모듈 경계는 다음과 같다.

```js
const planning = mountOrderPlanning({ element, onSelect });
planning.update(data, selectedId);
```

지도는 고객 뷰어와 같은 로컬 MapLibre·OFM 스타일 자산을 사용한다. `/scenario/api/route-data`에 등록된 실제 좌표와 배송 ID를 연결해 DSV 목적지 마커를 표시하며 현재는 V1 배송지 8곳만 지도에 나타난다. 선택 차량에 좌표 없는 배송지가 있으면 임의 좌표나 직선 경로를 만들지 않고 위치 미등록 건수를 표시한다. 실제 좌표가 추가되면 같은 ID 연결로 마커를 늘린다.

차량과 배송지는 수신 데이터에서 읽는다. 본문에 상시 노출된 배송량 편집기를 두지 않는다. 지도 모서리의 `지도 시나리오` 팝업은 수신한 전체 배송의 박스 합계를 기준 100%로 삼고 목표 물량을 80%부터 120%까지 미리 본다. 기본값과 초기화 값은 100%다. 이 값은 브라우저의 요약에만 적용하며 원본 스냅샷, 개별 주문 박스 수, 지도 주문 마커, 차량·배송지 수, 배송 상태, ETA, 알림과 배차 순서를 바꾸지 않는다. 60박스당 필요 차량 추정이나 임의 균등 배분을 하지 않는다. 기준값 누락은 `미확인`, 명시적인 빈 배열이나 합계 0은 0으로 유지한다. 자동 증가와 연속 애니메이션도 사용하지 않는다.

80–120% 미리보기는 향후 배차 알고리즘 성능 평가를 준비하는 입력 경계다. 실제 주문별 증감 배분 방식, 알고리즘 실행 시나리오와 평가 지표는 정제 데이터와 배차 계약이 마련될 때 정하며, 이번 범위에서는 실데이터 importer나 평가 프레임워크를 만들지 않는다.

실시간 갱신이 와도 사용자가 고른 차량과 지도 시나리오 값을 불필요하게 초기화하지 않는다. 지도 목적지 마커를 선택하면 전체 뷰어의 선택 배송을 갱신한다.

## 배송 목록

배송 목록은 수신한 전체 차량과 배송지를 조회한다. 차량, 상태, 배송지, 주소와 배송원으로 전체 데이터를 검색하거나 필터링하고 결과를 50개씩 페이지로 표시한다. 각 배송지는 데스크톱에서 44px 높이의 한 행으로 표시하고, 줄을 여러 겹 쌓는 기존 구조를 사용하지 않는다. 행에는 차량, 배송 순서, 배송지, 상태, 고객 시간대와 운영 정확 ETA 가운데 확인된 값만 간결하게 둔다.

행을 선택하면 별도의 선택 배송 카드에서 주소, 차량, 박스, ETA와 배송팁을 확인한다. 배송팁은 배송원이 배송지에 대해 직접 작성한 값이다. 목록 행과 선택 카드가 같은 상세 내용을 동시에 반복하지 않도록 행은 식별과 비교에 필요한 값만 가진다. 합성 배송지의 `미확인` 값은 그대로 보여 주며 실시간 V1 경로로 연결하거나 ETA를 만들어 내지 않는다.

## 배송 관제

배송 관제의 주 대상은 선택 배송 한 곳이다. 본문에서 선택 배송의 운영 정확 ETA, 고객 안내 시간대, 실제 도착, 배송 완료, 타임라인과 사건 이력을 보여 준다. 같은 배송지의 이름, 주소, ETA와 상태를 우측 패널에서 다시 카드로 반복하지 않는다.

우측 배송지 목록은 선택 배송이 속한 차량 한 대의 배송지만 표시한다. V1은 실시간 8곳, 합성 차량은 해당 차량의 예시 35곳이다. 배송 순서 편집과 보류/복원은 원본 동작을 가진 실시간 V1에만 제공한다. 합성 배송지를 선택해도 V1 편집기로 연결하지 않는다.

장치 표시는 제거한다. 관제 본문의 탭은 `사건 이력`과 `고객 알림`을 구성하고, 고객 알림 탭은 시각, 대상 배송지, 제목과 내용을 시간순으로 보여 준다. 우측 탭은 `배송지 목록`과 실시간 V1에서만 여는 `배송 관리`로 한정한다. 운영자는 선택 배송을 대상으로 최대 300자의 안내 문구를 입력하고 팝업 확인 후 시연 알림을 기록할 수 있다. 팝업에는 대상과 실제 외부 발송이 없는 시연 기록임을 알 수 있는 문구를 둔다.

ETA 진행 영역의 실제 도착과 배송 완료는 하나의 정상적인 경계선 체계로 그린다. 두 칸이 맞닿는 가운데에는 한 개의 구분선만 두고, 좁은 화면에서 쌓일 때 중복되거나 끊어진 테두리가 생기지 않아야 한다.

## 고객과 배송원 뷰어

고객 뷰어는 정확 ETA 대신 `customerWindowText`를 보여 준다. 최초 ETA가 13:30이면 고객 약속 시간대는 13:00부터 14:00까지다. 운영 뷰어의 `preciseTimeText`는 재계산할 때마다 갱신한다.

고객 약속 기준은 초기화 또는 최초 ETA 산출 때 정차지별로 설정한다. 이후 정확 ETA가 이 기준보다 늦게 30분을 초과한 순간에만 지연 알림을 한 건 추가하고, 그 정확 ETA를 새 기준으로 삼아 고객 시간대를 갱신한다. 29분과 30분 지연은 알리지 않는다. 15분 뒤 다시 16분이 누적되어 총 31분이 되면 알린다. 같은 ETA를 다시 계산해도 새 기준 대비 변동이 없으므로 반복 알림을 만들지 않는다. ETA가 앞당겨진 경우에는 고객 기준과 시간대를 바꾸지 않고 지연 알림도 만들지 않는다.

고객 뷰어가 연결될 때 이미 있던 알림은 이력으로만 표시한다. 같은 `boot` 안에서 해당 고객에게 새로 추가된 알림 ID만 한 번 팝업으로 보여 준다. 서버가 재시작되어 `boot`가 바뀌면 알림 ID 추적 상태를 새로 시작하되, 초기 스냅샷 전체를 새 팝업으로 재생하지 않는다. 자동 ETA 알림은 고객 시간대를 사용하고, 운영자가 직접 작성한 `manual` 알림은 ETA 형태의 시각이 들어 있어도 작성한 본문을 그대로 보여 준다.

배송원 뷰어는 선택 배송이 속한 차량 문맥으로 전환하고 각 배송지의 배송팁을 확인하며 최대 500자의 팁을 편집한다. V2 배송지를 선택하면 예시 배송원 002를 보여 주고 저장된 팁 작성자도 같은 이름을 사용한다. 합성 차량에서는 V1 현재 목적지나 배송 완료 동작을 제공하지 않는다. 저장이 서버 상태로 확인되기 전까지 완료 문구를 보여 주지 않는다. 사용자가 입력 중일 때 수신한 실시간 스냅샷은 입력값을 덮어쓰지 않는다. 다른 뷰어에는 저장 확인 뒤 같은 팁이 반영된다.

## 게이트웨이 명령과 검증

```js
{ type: "send_customer_notice", stopId, body }
{ type: "set_delivery_tip", stopId, body }
{ type: "set_scenario", scenario, stopId }
```

두 명령은 인증된 세션과 같은 Origin의 WebSocket에서만 처리한다. `stopId`는 현재 스냅샷에 존재하는 실시간 또는 합성 배송지여야 한다. 고객 안내 `body`는 앞뒤 공백을 제거한 뒤 1자 이상 300자 이하, 배송팁은 1자 이상 500자 이하다. 서버는 CRLF를 LF로 정규화한다. 탭과 줄바꿈은 허용하지만 그 밖의 C0 제어 문자, DEL, `<`, `>`를 포함한 값은 거절한다. 문자열이 아니거나 길이를 넘거나 알 수 없는 배송지면 상태를 바꾸지 않고 오류를 반환한다.

성공한 고객 안내는 제목 `운영자 안내`, `kind: "manual"`, 채널 `고객 팝업`, 상태 `시연 발송`, 인증 사용자 표시 이름, 시각과 대상을 가진 알림 한 건을 생성한다. 성공한 배송팁은 선택 차량의 시연 배송원 이름과 갱신 시각과 함께 저장한다. 두 변경은 모든 연결된 뷰어에 같은 스냅샷으로 전파한다. 외부 앱 푸시, 카카오 알림톡 또는 실제 배송원 장치로 전송하지 않는다.

명령 속도 제한은 WebSocket 연결이 아니라 로그인 사용자 이름을 기준으로 공유한다. 한 사용자의 모든 연결을 합쳐 이동식 1초 구간에서 10개 명령을 허용한다. 11번째 명령을 보낸 연결만 코드 `4429`로 닫고 같은 계정의 다른 연결은 유지한다. 시뮬레이션 초기화나 새 알림 이력은 서버의 속도 제한 구간을 비우지 않으며, 해당 기록은 1초가 지나면 자연스럽게 만료된다.

`set_scenario`의 `scenario`는 `received`, `picking`, `ready`, `shipping`, `arrived`, `completed`만 허용하고 `stopId`는 실시간 V1의 `S1`부터 `S8`까지만 허용한다. 여섯 프리셋은 임의 순서로 즉시 선택할 수 있다. 현재와 다른 선택은 상태를 한 번 계산하고 자동 진행을 시작하지 않는다. 같은 프리셋과 배송지를 다시 선택하면 계산과 상태 전파를 하지 않는다. 프리셋 변경은 배송팁과 운영자 수동 안내를 보존한다. 합성 배송지는 변경 명령을 보내지 않고 읽기 전용 사유를 표시한다.

프리셋과 배송 순서 변경은 기존 고객 약속 시간대와 운영 정확 ETA 기준을 전체 초기화하지 않는다. `arrived`와 `completed`는 선택 배송의 고정 실제 도착 시각을 `preciseTimeText`로 제공한다. 기존 고객 약속이 없을 때만 이 시각을 기준으로 최초 시간대를 만들며, 전체 약속과 정확 ETA 기준을 새로 만드는 동작은 명시적 `reset`뿐이다.

원시 스냅샷과 어댑터 최상위의 `scenarioPreset`은 현재 여섯 값 또는 `null`, `scenarioStopId`는 `S1`부터 `S8` 또는 `null`이다. 초기화는 `received`와 `S1`을 설정한다. 배송 순서 변경, CAS 저장이나 보류처럼 현재 프리셋 의미를 깨는 변경 뒤에는 두 값이 `null`일 수 있다.

이전 WebSocket 명령 `advance`, `place_order`, `speed`, `traffic`, `dwell`은 상태를 바꾸지 않는다. 배송원 화면의 기존 `arrive_stop`, `complete_stop` 명령은 유지하고 각각 `arrived`, `completed` 프리셋의 단일 전환으로 연결한다. `/scenario/` 화면 요청은 대응하는 합본 화면으로 이동하되 원본 회귀 검증에 필요한 route data와 공용 정적 자산은 유지한다.

## 실행 순서와 완료 조건

1. 게이트웨이 래퍼에서 다차량 표본, 배송팁, 알림과 고객 시간대 정책을 만든다.
2. 주문 배차 지도와 지도 모서리의 브라우저 전용 시나리오 설정을 연결한다.
3. 배송 목록을 수신 데이터 크기의 44px 단일 행 구조로 바꾸고 선택 카드에 배송팁을 둔다.
4. 배송 관제의 중복 배송지 표현과 장치 표시를 제거하고 고객 알림 탭, 운영자 팝업과 정상 테두리를 적용한다.
5. 고객 시간대와 신규 알림 팝업, 배송원 팁 편집을 연결한다.
6. 자동 진행, 배속, 차량 사고와 정차 지연 버튼을 제거하고 여섯 수동 프리셋을 연결한다.
7. [다차량 운영 테스트 명세](fleet-operations-test-spec.md)와 [수동 시나리오 테스트 명세](manual-scenarios-test-spec.md)를 로컬에서 검증한다.

로컬 자동 테스트와 세 해상도 브라우저 검증 뒤에는 별도 릴리스 SHA로 배포하고, 운영 서비스 상태와 인증된 HTTPS 화면을 확인해야 완료로 기록한다.
