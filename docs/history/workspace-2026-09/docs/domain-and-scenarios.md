# 배송 도메인과 시연 시나리오 초안

> **초기 디자인·정적 데모 이력.** 이 문서는 현재 구현·운영 서버의 상태를 나타내지 않습니다. [현행 저장소 문서](../../../README.md)를 먼저 사용하세요. 원문은 당시 판단의 근거로 보존합니다.

이 문서는 UI가 표현해야 할 의미를 정의합니다. API 명세·DB 설계·ETA 산식이 아닙니다. 원문의 확정 요구, 원문 예시, 데모 제안을 구분합니다. 아래 이름·시각·순서는 전부 합성 예시이며 실제 주문에서 가져오지 않았습니다.

박상현님은 시나리오 기반 B&W 기능·알고리즘 구현, 임지인님은 UI/UX 디자인 레퍼런스와 아키텍처를 담당합니다. 아래 값은 UI 검토용 표본이며 상현님의 구현에 고정 산식을 요구하지 않습니다. 양쪽에서 사용할 입력·결과 정의는 [아키텍처](architecture.md)를 기준으로 맞춥니다. 미트박스의 기존 시스템·API 존재는 전제하지 않습니다.

## 기본 단위

| 용어 | UI 준비를 위한 의미 | 미확정 사항 |
|---|---|---|
| 주문 | 고객이 조회하는 구매 요청의 식별 단위 | 한 주문의 여러 배송·박스 분할 여부 |
| 배송 건 | 운영 목록의 한 행 후보 | 주문과 1:1이라는 전제는 확정되지 않음 |
| 박스 | 배송 물량 단위 | 주문·배송 건과의 실제 관계 |
| 착지 | 배송 방문 지점 | 여러 주문이 같은 방문에 묶이는 규칙 |
| 배송 단계 | 주문 준비와 운송 진행의 현재 단계 | 전환 이벤트와 고객 노출 정책 |
| 배송 순서 | 현재 계획에서 해당 방문의 순서 | 최초 순서인지 남은 순서인지 |
| ETA 범위 | 고객에게 보여줄 도착 예정 시간 구간 | 범위 산출·축소 규칙 |
| 점 예측 | 정확도 평가에 필요할 수 있는 단일 예측 시각 | 계산 담당이 정의. 범위 중간값으로 임의 대체 금지 |
| 실제 도착 | ETA 평가의 기준이 될 현장 도착 사건 | 이벤트 정의와 수집 방식 |
| 배송 완료 | 고객 인도 또는 완료 처리 사건 | 실제 도착과 동일한 사건인지 확인 필요 |

첫 미리보기의 합성 사례만 주문 1건=배송 1건으로 단순화합니다. 이를 실제 서비스 계약으로 굳히지 않습니다. 합성 ID는 `DEMO-001`, 고객 이름은 `가상 식당 A`처럼 사용하고 실제 주소·전화번호는 넣지 않습니다.

## 원문 상태 예시의 보존

아래 아홉 표현은 첨부 2번의 예시입니다. 실제 운영에서 필수로 같은 순서로 발생한다고 가정하지 않습니다.

| 원문 표현 | 데모 분류 제안 | 표현 규칙 |
|---|---|---|
| 주문 접수 | 배송 단계 | 접수 사실과 시각 |
| 결제 완료 | 배송 단계 | 상위 시스템의 사건을 표시. 결제 기능 없음 |
| 피킹 중 | 배송 단계 | 준비 진행 상태 |
| 라벨 부착 | 배송 단계 | 스캔·라벨 사건의 합성 표본 |
| 상차 대기 | 배송 단계 | 출발·배송 중과 구별 |
| 배송 출발 | 배송 단계 | 출발 사건 이후 운송 진행 |
| X번째 순서 배송 예정 | 진행 정보 | 숫자와 기준 설명. 별도 생애주기 단계로 고정하지 않음 |
| 인근 배송 중 | 진행 정보 | 합성 인근 이벤트가 있을 때만 표시. 지도나 좌표 계산 없음 |
| 배송 완료 | 배송 단계 | 완료 시각을 표시하고 앞으로의 ETA와 구분 |

데모 분류는 지인님의 UI 준비를 위한 제안입니다. 고객 화면에서 일부 준비 단계를 묶을지는 미트박스에 확인합니다. “인근”을 거리 수치나 “곧 5분 내 도착”으로 변환하지 않습니다.

## 화면에 필요한 정보 묶음

| 묶음 | 필요한 내용 | 값이 없을 때 |
|---|---|---|
| 식별 | 가상 배송 ID, 가상 주문 ID, 고객 별칭 | 선택 대상 없음 |
| 현재 단계 | 단계명, 해당 사건 시각, 사건 원천 | 상태 확인 중 |
| 진행 | 순서 값과 기준, 인근 여부 | 순서 표시 생략 또는 확인 중. 0번째 금지 |
| ETA | 시작·종료, 예측 갱신 시각, 시간대 | 도착 예정 시간 확인 중 |
| ETA 변경 | 이전·현재 범위, 사유, 변경 사건 시각 | 이전 값 없으면 비교를 생략 |
| 이벤트 이력 | 사건 시각, 수신 시각, 종류, 설명 | 누락 사건을 자동 완료로 채우지 않음 |
| 완료 | 실제 도착 시각과 완료 시각을 별도 취급 | 완료 시각 미확인. 도착 시각 대입 금지 |
| 안내 미리보기 | 채널 종류와 고객에게 보일 문구 | 템플릿 준비 상태. 발송 성공으로 표시 금지 |
| 시연 문맥 | 시나리오 ID, 고정 기준시각, 합성 데이터 표식 | 시연 여부가 불분명한 화면을 만들지 않음 |
| 조합 확인 | 배송 결과 버전과 그 결과를 만든 시나리오 사건 | 같은 버전의 운영·고객 결과인지 미확인으로 구별 |

실제 연동 데이터의 필드명·전달 형식은 다음 단계에서 확인합니다. 이 표를 그대로 서버 계약으로 확정하지 않습니다.

## ETA 표현 규칙

1. 기본은 `13:00 ~ 14:00 도착 예정` 같은 시간 범위입니다. 예시는 첨부 3번에 근거합니다.
2. UI에서 미래 시점을 임의 계산하지 않습니다. 준비 단계는 합성 표본을, 조합 단계는 상현님의 시나리오 구현이 제공하는 이전·현재 값을 같은 의미로 표현합니다.
3. 범위의 양 끝이 같은 폭으로 이동한 경우만 `20분 늦어짐`처럼 한 숫자로 표시합니다. 폭이 달라지면 두 범위를 나란히 보여주고 임의의 평균 변화량을 만들지 않습니다.
4. 순서 변경·교통 지연·정차 지연은 변경 사유입니다. “변경됨”과 “고객 약속 위반”은 다른 의미입니다. 약속 기준 미확정 상태에서 지연 위반률을 만들지 않습니다.
5. 미확정·갱신 중·마지막 정보가 오래됨·갱신 실패는 구분합니다. 자동 오래됨 판정의 시간 임계값은 미확정이며 데모에서는 명시된 표본으로만 보여줍니다.
6. 기존 ETA가 있는 갱신 실패 사례에서는 마지막 값과 그 갱신 시각·실패 상태를 함께 보여줍니다. 새 예측처럼 표시하지 않습니다.
7. 완료 후에는 `13:42 배송 완료`가 주 정보입니다. 마지막 예상 범위는 필요한 경우 이력에 남깁니다. 완료를 실제 도착과 자동 동일시하지 않습니다.
8. 시나리오 시각은 2026-09-16, Asia/Seoul 기준의 고정 값입니다. 자정 경계는 날짜까지 표시하고 현재 시스템 시계에 따라 달라지지 않게 준비할 예정입니다.

## 지표와 목표

첨부의 지향 기준은 **실제 도착 시점 대비 ±15분 이내 80% 이상**이며, 초기에는 60~70% 등 단계적 목표를 설정할 수 있다고 적혀 있습니다. 이는 성능 측정 결과나 이번 데모의 통과 기준이 아닙니다.

| 항목 | 후속 UI 표시 제안 | 지켜야 할 의미 |
|---|---|---|
| 전체·배송 중·배송 완료 건수 | 합성 표본의 건수만 표시 가능 | 동일 시점·동일 필터의 모집단 사용 |
| ETA 변경 건수 | 부가 건수로 표시 가능 | 배송 단계와 겹치는 속성이므로 다른 단계 건수와 합계로 더하지 않음 |
| 미확정 ETA 건수 | 필요하면 별도 표시 | 실제 0건과 데이터 부재를 구별 |
| ETA 정확도 | `목표 80% 이상 · 현재 측정 전` 같은 내부 설명 | 고객 주 화면에는 노출 불필요. 합성 데이터로 달성률 주장 금지 |
| 시간 범위 내 도착 비율 | 현재 계산·표시하지 않음 | ±15분 점 예측 정확도와 다른 지표 |

정확도를 평가하려면 실제 도착 정의, 비교할 예측의 생성 시점, 점 예측값, 대상 기간·모집단, 결측·취소·재시도 처리, 시간대가 먼저 정해져야 합니다. 배송 완료 시각만 있거나 ETA 구간만 있는 것으로 ±15분 정확도를 계산하지 않습니다.

## 시연 시나리오 후보

한 배송 건을 중심으로 정상 진행을 보여주고, 변경 원인은 서로 독립된 분기로 검토합니다. 아래는 스토리보드 초안이며 동작 코드나 fixture 파일은 없습니다.

기준 분기 B: `DEMO-001 / 가상 식당 A`, 11:30 배송 출발, 현재 계획 순서 5번째, 11:30 갱신된 ETA `13:00 ~ 14:00`. 여기서 “5번째”는 데모의 현재 계획 순서라는 가정입니다.

| ID | 시작과 합성 사건 | 운영 화면에 필요한 변화 | 고객 미리보기 | 근거 |
|---|---|---|---|---|
| S1 준비 | 11:20 상차 대기, ETA 미확정 | 준비 이력과 확인 중 상태 | 상차 대기, 도착 시간 확인 중 | T2-02, T3-02 |
| S2 출발 | 기준 분기 B | 출발, 순서 5, ETA 범위와 갱신 시각 | 13:00~14:00 예정, 배송 진행 | T2-01, T2-04 |
| S3 순서 변경 | B에서 11:40 순서 5→3, ETA 12:40~13:40 | 이전·현재 범위, 20분 앞당겨짐, 순서 변경 사유 | 새 범위와 순서. 알림은 정책 확인 후 표본 선택 | T3-04 |
| S4 교통 지연 | B에서 11:45 합성 교통 지연, ETA 13:20~14:20 | 20분 늦어짐, 교통 지연, 갱신 시각 | 새 범위와 시간 변경 안내 미리보기 | T3-04, T3-05 |
| S5 정차 지연 | B에서 11:50 앞 배송지 정차 지연, ETA 13:30~14:30 | 30분 늦어짐, 정차 지연, 이전 범위 | 새 범위와 변경 안내 미리보기 | T3-04, T3-05 |
| S6 인근·완료 | B에서 13:20 인근 사건, 13:42 완료 사건 | 진행 표시 후 배송 완료와 완료 시각 | 인근 배송 중 → 13:42 배송 완료 | T2-02, T2-04 |
| S7 정보 미확정 | B에서 11:50 갱신 실패 표본 | 마지막 ETA·11:30 갱신·최신 정보 확인 필요 | 최신 도착 시간 확인 중, 마지막 정보 구분 | UI 보완 제안 |

S3·S4·S5는 앞 분기의 값을 누적하지 않고 B로 돌아가 시작합니다. S6의 실제 도착 시각은 의도적으로 제공하지 않아 완료 시각과 구별합니다. 인근 여부와 지연값은 가상 사건이며 지도·교통 API·모델에서 계산된 결과가 아닙니다. 정차 시간이 몇 분이면 재계산할지는 원문에 수치가 없어 확정하지 않습니다.

알림은 `앱 푸시 미리보기`, `알림톡 미리보기`라는 라벨과 문구만 검토합니다. 실제 발송·전달·수신 여부는 없습니다. 주요 상태 전환은 원문 요구이지만 모든 ETA 변경이 고객 알림을 유발한다고 가정하지 않습니다.

## 후속 UI 검토 항목

- 같은 시나리오의 운영 상세와 고객 미리보기에서 상태·시간 범위·갱신 시각이 일치하는가?
- UI가 시나리오 로직을 복제하지 않고 합의된 배송 결과를 읽으며, 조회 필터가 그 결과 자체를 바꾸지 않는가?
- 독립 분기와 초기화가 이전 시나리오의 값·메시지를 남기지 않는가?
- ETA 없음, 이전 ETA 없음, 범위 폭 변화, 날짜 경계, 긴 사유를 구별해 표현하는가?
- 지연 없는 ETA 변경을 오류로 오해하게 하지 않는가?
- 알림 표본이 실제 발송 결과처럼 보이지 않는가?
- 지도·실시간 연결·검증되지 않은 정확도 표기가 없는가?

위 항목은 향후 미리보기 제작 시 확인할 계약입니다. 이번 단계에서 UI 테스트가 실행되었다는 의미는 아닙니다.
