# UI와 시나리오 구현을 연결하는 구조

> **초기 디자인·정적 데모 이력.** 이 문서는 현재 구현·운영 서버의 상태를 나타내지 않습니다. [현행 저장소 문서](../../../README.md)를 먼저 사용하세요. 원문은 당시 판단의 근거로 보존합니다.

상태: **로컬 UI 경계 구현 · 실제 공급자 연결 미착수**. 2026-09-13 사용자의 역할 정의와 현재 합성 미리보기를 반영합니다.

이번 목표는 배송 트래킹·ETA의 시나리오 구현과 UI/UX를 분리해 준비하고, 같은 입출력 정의로 조합할 수 있게 하는 것입니다. 미트박스의 기존 배송 시스템·API 유무는 미확인입니다. 외부 연결은 향후 선택할 수 있는 데이터 공급 방식으로만 남깁니다.

## 역할과 함께 맞출 부분

| 담당 | 책임 | 서로 맞출 부분 |
|---|---|---|
| 박상현 | 시나리오 기반 B&W 기능·알고리즘 구현 | 시나리오 입력, 단계 변화, ETA 결과, 초기화 동작 |
| 임지인 | UI/UX Design Reference With Architecture | 시각 체계·Asset Page·컴포넌트, 도메인 표현, 데이터와 화면의 경계 |

상현님의 B&W 화면은 시나리오의 기능을 확인하는 작업물입니다. 지인님은 그 로직을 다시 만들지 않고 입력과 결과가 UI에 어떻게 연결될지를 정의합니다. 상세 입출력은 양쪽 작업에서 합의할 대상이며, 현재 이미 완성된 구현이 있다고 가정하지 않습니다.

## 최소 구조와 현재 로컬 구현

하나의 프로젝트 안에서 다음 책임만 나눕니다. 현재 `previews/terminal-view/`에 정적 로컬 UI와 합성 데이터 경계를 구현했으며, 상현님 시나리오 결과나 외부 API는 연결하지 않았습니다.

| 경계 | 맡을 일 | 규칙 |
|---|---|---|
| 도메인·입출력 정의 | 배송 식별자, 상태, 순서, ETA 범위, 갱신 시각, 변경 사유 | 화면 모양과 독립적으로 의미를 정의. 입력 사건과 조회 결과의 형태는 각각 정의 |
| 시나리오 구현 | 입력 사건에 따른 상태·ETA 결과와 초기화 | 상현님 구현 영역. 디자인·색상·레이아웃에 의존하지 않음 |
| API·데이터 접근 | UI가 결과를 조회하고 허용된 시나리오 동작을 요청하는 창구 | 현재 `view-model.mjs`가 `sample-data.mjs`의 합성 결과를 사용. 실제 공급자가 정해지면 이 경계에서 교체 |
| Config | 표기, 시간대, 선택 가능한 시나리오 등 실제로 바뀔 설정 | 상태 전이·ETA 계산을 숨겨 넣지 않음. 비밀정보를 브라우저 설정에 넣지 않음 |
| UI·조회 필터 | 결과 표현, 상태·기간·변경 여부로 조회, 고객 미리보기 | 필터로 원본 사건이나 계산 결과를 바꾸지 않음 |

현재 `view-model.mjs`는 hash route와 조회·선택 결과를 만들고, `view-components.mjs`는 배송 현황·단말 관제·고객 보기·디자인 가이드가 공유하는 ETA·배지·알림·고객 카드 표현을 제공합니다. 구체 필드와 초기화 의미는 [UI 데이터 연결 명세](ui-data-contract.md)에 기록했습니다.

API 계약은 UI와 데이터 제공자가 주고받는 약속입니다. 시나리오의 로컬 구현을 먼저 붙일 수 있으며, HTTP 서버·실제 외부 API·SDK가 지금 존재해야 한다는 뜻은 아닙니다. 함수 호출에서 HTTP로 바뀌더라도 입력·결과의 의미와 오류 표현을 유지하는 방향입니다.

`API`, `Config`, `filter`라는 단어마다 독립 서비스를 만들 필요는 없습니다. API·데이터 접근은 한곳에, 설정은 선언적인 값으로, 조회 필터는 조회 영역에 둡니다. 접근 권한이나 고객에게 제공할 필드 제한은 후속 API 경계에서 다룰 사항이며 화면 필터와 구별합니다.

## 먼저 맞출 입출력

| 구분 | 최소 내용 | 확인할 것 |
|---|---|---|
| 시나리오 입력 | 시나리오 ID, 배송 ID, 사건 종류, 고정 시각, 필요한 순서·조건 | 허용된 사건과 분기·초기화 규칙 |
| 배송 조회 결과 | 현재 단계, 진행 정보, ETA 범위, 갱신 시각, 변경 사유, 결과 버전 | 미확정·변경·완료를 어떻게 구분하는가 |
| 동작 결과 | 반영 여부, 처리 중·실패·지원하지 않는 입력의 설명 | 버튼 요청과 실제 상태 반영을 혼동하지 않는가 |
| 조회 조건 | 상태, 기간, ETA 변경 여부 | 목록과 건수 요약이 같은 조건을 쓰는가 |

필드명과 API URL은 아직 확정하지 않습니다. [도메인 문서](domain-and-scenarios.md)의 상태·시간 정의를 기반으로 구체화합니다. UI 내부에 별도의 상태 전이·ETA 계산을 넣지 않습니다.

## 화면에서 보여줄 투명성

운영 상세에서 **어떤 사건이 들어왔는지 → 상태·ETA가 어떻게 바뀌었는지 → 고객에게 어떤 정보가 보이는지**를 따라갈 수 있게 합니다. 시나리오 사건의 시각, 변경 전후 값, 사유, 갱신 시각을 활용합니다. 코드·JSON 표시는 필요한 경우 「데이터 예시」를 펼쳤을 때만 둡니다.

고객 미리보기는 같은 배송 결과를 사용하는 소비 예제입니다. 미트박스의 실제 화면을 재현했다거나, 고객이 반드시 이 화면을 사용해야 한다는 의미는 아닙니다. 운영·고객용 표현이 같은 결과 버전을 사용하면서도 각자 필요한 필드만 보여주는지 확인합니다.

이번 핵심 시연은 기존 S1~S7의 배송·ETA 시나리오입니다. 별도 연동 관리 콘솔·연결 설정 편집기·Webhook 전달 대시보드는 추가하지 않습니다. 실제 외부 시스템이 확인되면 필요한 연결 방식과 원천 코드 매핑을 그때 정합니다.

## 조합 확인 기준

- UI의 레이아웃을 바꿔도 상현님의 시나리오 로직을 고치지 않는가?
- 시나리오 데이터 공급자를 바꿀 때 화면 전체가 아니라 데이터 접근 경계에서 연결할 수 있는가?
- 같은 결과 버전의 상태·ETA·변경 사유가 운영 화면과 고객 미리보기에서 일치하는가?
- Config나 조회 필터 변경이 배송 상태 전이·ETA 결과를 임의로 바꾸지 않는가?
- 사건 입력·동작 요청과 반영 결과를 구별하고, 초기화가 이전 분기의 결과를 남기지 않는가?

로컬 합성 UI에서는 Node 테스트 7개와 실제 브라우저의 메뉴·선택·히스토리·필터·초기화·키보드·플로팅 팝업 회귀, 8개 시나리오의 관제·TMS·고객 ETA 일치를 확인했습니다. 상세 증거는 [UI 검증 기록](ui-verification.md)을 따릅니다.

이는 로컬 표현과 경계의 검증이며 실제 공급자 통합 검증은 아닙니다. 상현님 구현과 합의한 결과를 연결한 뒤 위 기준을 다시 확인해야 합니다. HTTP API의 입출력을 구현과 독립적으로 기술하는 참고 자료는 [OpenAPI 공식 명세](https://spec.openapis.org/oas/latest.html)이며, 도구·명세 버전 채택은 보류합니다.
