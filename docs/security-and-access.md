# 보안과 접근

이 문서는 현재 저장소에서 확인되는 보안 통제와 남은 접근 통제 공백을 구분한다. 실서버 방화벽, IAM, SSH, Caddy 런타임 설정, 인증서, 계정 현황을 조회한 결과가 아니다. 실제 운영 상태는 [운영 런북](operations.md)의 읽기 전용 점검과 별도 인프라 검토로 확인해야 한다.

## 핵심 판단

현재 시스템은 **초대 기반 로그인으로 전체 화면과 API를 가리는 검토자용 게이트웨이**다. 인증은 구현되어 있지만 역할별 권한은 구현되어 있지 않다. 로그인한 사용자는 서버가 제공하는 전체 날짜·차량·주문 데이터를 읽고 배차·운행·자원 변경 API를 호출할 수 있다.

따라서 현재 계정을 운영자, 배송원, 고객 계정으로 간주하거나 실제 사용자에게 직접 발급하면 안 된다. 배송원별 배차, 고객별 주문, 운영자 권한을 서버에서 구분하기 전까지 모든 로그인 계정은 신뢰된 내부 검토자 권한으로 취급한다.

## 현재 구현된 통제

### 인증과 세션

- 가입은 일회용 초대 코드가 필요하다. 서버는 초대 코드의 SHA-256 해시만 계정 파일에 저장한다.
- 사용자 이름은 소문자로 정규화되고 3~40자의 제한된 ASCII 문자만 허용한다.
- 비밀번호는 8~128자이며 무작위 salt와 scrypt로 해시한다.
- 세션 토큰은 32바이트 난수로 만들고 서버 메모리에는 토큰의 SHA-256 해시만 저장한다.
- 세션 유효 기간은 8시간이다. 세션은 프로세스 메모리에만 있으므로 재시작하면 모두 만료된다.
- 쿠키는 `HttpOnly`, `SameSite=Strict`, 경로 `/`를 사용한다. `PUBLIC_ORIGIN`이 HTTPS이면 `Secure`도 설정한다.
- 비활성화된 사용자는 다음 HTTP 세션 확인에서 거절된다. 열린 WebSocket도 주기적 확인 또는 다음 메시지 처리에서 닫힌다.
- 로그인·가입 시도는 IP별 15분 동안 20회로 제한한다. 제한은 프로세스 메모리 기반이며 재시작·다중 복제본 사이에 공유되지 않는다.

### 요청 경계

- 로그인 이후의 일반 페이지와 API는 공통 인증 미들웨어 뒤에 있다.
- POST/PATCH 변경 요청은 정확한 `PUBLIC_ORIGIN`과 일치하는 `Origin` 헤더를 요구한다.
- WebSocket은 정확한 경로, `Origin`, 유효 세션을 모두 확인한다.
- 날짜별 명령은 사용자별 분당 120회, 레거시 WebSocket 명령은 사용자별 초당 10회로 제한한다.
- 배차 명령은 서버 boot와 revision을, 자원 변경은 resource revision을 확인한다.
- 애플리케이션은 strict routing, 단순 query parser, 요청 본문 크기 제한을 사용한다.

### 브라우저와 네트워크

- 공통 응답은 `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`을 설정한다.
- CSP는 기본적으로 same-origin만 허용하고 지도 타일·지정 CDN·WebSocket 등 명시된 출처만 추가한다. `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`을 사용한다.
- Node 서버는 `127.0.0.1`에만 바인딩한다. 저장소의 Caddy 템플릿이 외부 HTTPS를 종료한다.
- systemd 템플릿은 전용 사용자, `NoNewPrivileges`, `PrivateTmp`, 읽기 전용 시스템, 보호된 홈, 제한된 쓰기 경로를 사용한다.

이 통제는 저장소에서 확인한 구현 계약이다. 실제 프록시 헤더, 방화벽, 보안 그룹, 인증서 갱신, 파일 권한이 일치하는지는 운영 환경에서 따로 검증해야 한다.

## 확인된 권한 공백

### 역할 기반 권한 없음

계정 레코드와 `publicUser()`에는 사용자명, 표시 이름, 생성 시각만 있다. 역할, 조직, 차량, 주문, 고객 소유권이 없다. 서버는 운영자와 검토자, 배송원과 자기 배차, 고객과 자기 주문, 계정 관리자와 일반 사용자, 읽기 전용 사용자와 변경 사용자를 구분하지 못한다.

화면에서 버튼을 숨겨도 보안 통제가 되지 않는다. 모든 권한 검사는 API와 WebSocket 서버에서 수행해야 한다.

### 감사 기록 부족

- 날짜별 사건과 알림은 업무 상태 일부를 저장하지만 모든 명령의 인증 주체, 이전값, 이후값, 요청 ID를 불변 감사 로그로 남기지 않는다.
- 수동 고객 알림의 `author`는 command 입력에서 받아 표시하므로 인증 주체의 신뢰 가능한 감사 필드가 아니다.
- 자원 DB는 revision을 증가시키지만 누가 어떤 값을 변경했는지 기록하지 않는다.
- 로그인 성공·실패, 초대 발급, 계정 비활성화에 대한 중앙 감사 로그 계약이 없다.
- Node 오류 로그는 오류 이름만 출력한다. 프록시 또는 플랫폼 로그는 이 저장소에서 정의하지 않는다.

현재 사건·알림·revision을 보안 감사 로그나 부인 방지 증거로 사용하면 안 된다.

### 증빙과 외부 전달 미연결

- 배송 사진은 포함된 예시 이미지 또는 파일 선택으로 만든 `URL.createObjectURL()`을 미리본다. 현재 ‘사진 촬영’ 동작에는 예시 이미지를 사용하는 경로가 있다. 사진 파일은 서버에 업로드되지 않는다.
- 완료 API는 `hasPhoto: true`와 필수 요청 ID를 검사하지만 서버가 사진 존재·내용·촬영 시각·주문 연결을 검증하지 않는다.
- 고객 알림은 애플리케이션 상태의 기록과 화면 표시다. 외부 푸시·문자·알림톡 접수 또는 기기 도달 증거가 아니다.
- 차량 위치의 `source: demo`와 계획 ETA를 실제 GPS·실측 ETA로 취급하면 안 된다.

비밀번호 해시와 초대 해시는 평문이 아니지만 공개 가능한 데이터가 아니다. 계정 파일 유출은 오프라인 비밀번호 추측과 사용자 목록 노출로 이어질 수 있으므로 비밀로 취급한다.

## 최소 권한 운영

### 서비스 계정

- Node 프로세스는 전용 비로그인 계정으로 실행한다.
- 릴리스와 데이터셋은 읽기 전용으로 제공한다.
- 쓰기 권한은 계정, 체크포인트, 자원 DB가 있는 승인된 상태 디렉터리로 제한한다.
- Caddy와 Node 서비스의 계정·데이터 디렉터리를 분리한다.
- 운영자가 CLI를 실행할 때도 서비스 사용자로 실행하여 소유권을 유지한다.

### 사람과 계정

- 현재 로그인 계정은 전체 권한이므로 필요한 내부 검토자에게만 발급한다.
- 개인별 계정을 사용하고 공용 계정 사용을 피한다.
- 초대는 한 명·한 목적·짧은 유효 기간으로 발급한다.
- 검토 종료, 역할 변경, 의심 활동 발생 시 계정을 비활성화한다.
- 운영체제 접근, 백업 접근, 계정 발급 권한을 웹 검토 권한과 분리한다.
- 정기 접근 검토에서 사용자 존재, 발급 목적, 마지막 필요 시점, 비활성화 여부를 확인한다.

계정 비활성화는 서버 파일을 변경한다. [운영 런북](operations.md)의 승인·백업·실행 사용자 확인을 거친다.

## 로그와 공유 자료

- 요청 본문, `Cookie`, `Set-Cookie`, 비밀번호, 초대 코드를 기록하지 않는다.
- 계정 파일과 체크포인트를 `cat`, pretty-print, diff하지 않는다.
- 장애 티켓에는 전체 주소·좌표·고객명 대신 내부 상관 ID와 오류 코드만 남긴다.
- 브라우저 HAR, 스크린샷, 콘솔 덤프를 공유하기 전에 쿠키, URL 쿼리, 고객 정보, 지도 위치를 검토한다.
- `systemctl cat`이나 환경 덤프를 공유하기 전에 drop-in에 비밀값이 없는지 확인한다.
- 백업 해시는 내용 확인에 사용하되 백업 파일 자체를 일반 협업 도구에 첨부하지 않는다.

## 보안 사건 대응

### 계정 또는 세션 의심

1. 사용자명, 관측 시각, 영향 환경을 기록한다. 비밀번호나 쿠키를 수집하지 않는다.
2. 승인된 운영자가 계정을 비활성화한다.
3. 열린 WebSocket과 다음 HTTP 요청에서 비활성화가 적용되는지 확인한다.
4. 광범위한 세션 유출이면 서비스 재시작이 모든 메모리 세션을 만료시키지만 가용성에 영향을 준다. 사건 지휘 승인 후 수행한다.
5. 역할별 감사 로그가 없으므로 체크포인트, 자원 DB revision, 프록시·호스트 로그를 시간대별로 보존한다. 행위자를 확정할 수 없음을 기록한다.

### 초대 코드 노출

현재 CLI에는 특정 미사용 초대를 취소하는 명령이 없다. 노출된 코드가 미사용인지 계정 파일 내용을 일반 로그에 출력해 확인하지 않는다. 운영 책임자는 계정 저장소 백업과 영향 범위를 검토한 뒤 노출 초대의 만료를 기다릴지 제한된 계정 파일 변경 절차를 수행할지 결정한다. 임의 삭제나 계정 파일 전체 초기화는 금지한다.

### 민감 데이터 유출 의심

1. 공개 경로, 로그, 백업, 저장소 중 노출 위치를 읽기 전용으로 특정한다.
2. 원본 증거와 접근 시간을 보존하고 추가 복제를 중지한다.
3. 주문 데이터셋, 체크포인트, 계정 파일, 자원 DB 중 영향을 받은 자산을 분리한다.
4. 개인정보 대응 책임자에게 실제 포함 필드와 범위를 전달한다.
5. 삭제·회전·재발급은 증거 보존과 영향 분석 뒤 승인된 절차로 수행한다.

## 운영 전 필수 보완 사항

다음 항목은 현재 구현 사실이 아니라 실제 사용자 운영을 위한 요구사항이다.

| 우선순위 | 요구사항 | 완료 기준 |
| --- | --- | --- |
| P0 | 서버측 역할·소유권 검사 | 운영자, 배송원, 고객, 읽기 전용 역할을 정의하고 모든 HTTP·WebSocket 요청에서 객체 소유권을 검사한다. 다른 사용자 ID를 넣은 조회와 변경이 서버에서 거절된다. |
| P0 | 신뢰 가능한 감사 로그 | 인증 주체, 역할, 요청 ID, 대상, 이전/이후 revision, 결과, 시각을 변조 방지 저장소에 남긴다. 사용자 입력 `author`와 분리한다. |
| P0 | 서버측 배송 증빙 | 사진 업로드, 악성 파일 검사, 주문·배송원 연결, 보존·삭제 정책, 접근 통제를 구현하고 저장 성공 뒤에만 완료한다. |
| P0 | 내구성 있는 운영 저장소 | 단일 writer를 강제하거나 다중 프로세스에서도 안전한 저장소를 사용한다. 원자적 명령, 중복 처리 방지, 감사 기록과 검증된 백업·복원을 제공한다. |
| P1 | 중앙 속도 제한과 세션 정책 | 복제본 사이에 공유되는 제한, 강제 로그아웃, 세션 조회·회수, 비밀번호 재설정 정책을 제공한다. |
| P1 | 계정 관리 수명주기 | 초대 취소, 비밀번호 변경·재설정, 계정 만료, 마지막 로그인, 접근 검토를 제공한다. |
| P1 | 외부 연동 보안 | 기기 등록, 배송원 수신·수락, GPS 발신자 인증, 알림 공급자 자격 증명과 전달 상태를 분리한다. |
| P1 | 보안 관측과 경보 | 인증 실패 급증, 비정상 변경률, 409/500 증가, 체크포인트 쓰기 실패, 자원 DB 오류를 탐지한다. |
| P1 | 비밀 관리 | 파일·drop-in 평문 비밀을 중앙 비밀 저장소와 회전 절차로 이전한다. |

P0 항목이 완료되기 전에는 실제 배송원·고객 접근이나 증빙 기반 배송 완료를 운영 수준으로 선언하지 않는다.

## 검토 근거

- 인증·세션·파일 잠금: `lib/access.js`, `scripts/manage-access.js`
- HTTP·쿠키·Origin·CSP·WebSocket: `server.js`
- 날짜별 상태·명령·체크포인트: `lib/source-operations-router.js`, `lib/dispatch-operations.mjs`, `lib/source-operations.mjs`
- 자원 DB·API·v1 이행: `lib/resource-store.js`, `lib/resource-router.js`, `scripts/import-resource-catalog.mjs`
- 사진 브라우저 미리보기: `apps/combined/driver.mjs`
- 서비스·프록시 격리: `deploy/meatbox-gateway.service`, `deploy/Caddyfile`

이 목록은 코드 근거다. 실제 운영 설정과 데이터는 포함하지 않는다.
