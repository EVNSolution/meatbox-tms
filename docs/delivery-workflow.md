# 커밋·CI·배포 작업 기준

2026-10-06, Asia/Seoul. 사용자가 이 프로젝트의 배포를 상시 허용했고, 변경 목적별 커밋과 CI 중복 방지·배포 시간 최적화를 우선하도록 지시했다. 앞으로의 작업과 프로젝트 스킬은 이 문서를 따른다.

## 상시 허용과 완료 범위

요청받은 제품 작업에는 검증, 목적별 커밋, push, PR 작성·갱신, CI 확인, 설정된 환경 배포와 배포 후 확인이 포함된다. 같은 범위에서 매번 배포 허용을 다시 묻거나 로컬 수정만 끝내고 배포 여부를 사용자에게 넘기지 않는다. 현재 설정된 대상은 TEST 한 대다. QA·운영은 해당 환경이 구성되고 작업 대상이 정해졌을 때 적용한다.

배포 허용은 업무 자료 삭제·덮어쓰기, 사용자 권한 확대, 임의의 환경 생성 또는 다른 프로젝트 변경을 뜻하지 않는다. 자료와 계정, 단일 writer, 환경 격리, 활성 릴리스 비교, 백업·복구 검사는 유지한다. 자격 증명이나 배포 대상이 없으면 먼저 사용 가능한 정식 접근 경로를 확인하고, 해결할 수 없는 구체적인 장애만 보고한다.

## 변경 목적별 커밋

제목은 `접두사: 변경 이유` 또는 `접두사(범위): 변경 이유`로 쓴다. `Codex`를 커밋 접두사로 사용하지 않는다. 기존 이력은 이 규칙을 맞추려고 다시 쓰지 않는다.

| 접두사 | 적용 범위 |
| --- | --- |
| `Feat:` | 새 사용자 기능 |
| `Fix:` | 기존 동작·표시 오류 복구 |
| `Refactor:` | 동작을 유지한 구조 변경 |
| `Perf:` | 제품 실행 성능 개선 |
| `CI:` | 검증·배포 워크플로 변경 |
| `Build:` | 빌드·패키지 구성 변경 |
| `Test:` | 검증 추가·개선 |
| `Docs:` | 문서·작업 지침·스킬 변경 |
| `Chore:` | 위 분류에 속하지 않는 유지 관리 |

독립적으로 검토·되돌릴 수 있는 목적은 별도 커밋으로 나눈다. 한 오류의 코드·회귀 검사·출처 해시는 같은 `Fix:` 커밋에 둔다. 커밋 본문은 기존 Lore 계약의 `Constraint:`, `Rejected:`, `Confidence:`, `Scope-risk:`, `Directive:`, `Tested:`, `Not-tested:` 중 판단에 필요한 trailer를 유지한다. 중간 커밋마다 push하지 않고 검증된 변경 묶음을 한 번 push해 불필요한 CI 실행을 줄인다.

## CI 중복 방지

PR과 Actions는 별도 검사 시스템이 아니다. PR의 상태 검사는 Actions가 실행한 같은 결과다. 기능 브랜치 push와 PR 이벤트로 같은 후보를 두 번 검사하지 않는다. PR 갱신은 PR 이벤트 한 경로로, 기본 브랜치 변경은 기본 브랜치의 필요한 검증·배포 경로로 처리한다. 기존 실행이 있으면 그 실행을 기다리며 같은 SHA에 수동 실행을 덧붙이지 않는다. 새 커밋으로 대체된 PR 실행은 concurrency로 취소한다.

한 파이프라인 안에서 같은 테스트 파일, 설치, 빌드, 패키징을 반복하지 않는다. PR merge ref와 실제 기본 브랜치 HEAD가 다른 경우 이를 같은 후보라고 가정해 검증을 건너뛰지 않는다. 검증을 줄이는 대신 불필요한 이벤트·중복 명령을 제거한다. 기존 외부 보안 검사도 임의로 해제하지 않는다.

문서(`**/*.md`, `docs/`, `.codex/`)만 바뀐 PR은 검증 워크플로를 실행하지 않는다. 검증·패키징할 바이트가 없기 때문이며, 기본 브랜치 push는 변경 내용과 무관하게 항상 전체 검증과 패키징을 실행한다. TEST 배포 워크플로는 기본 브랜치의 검증 완료 이벤트에만 반응하고 PR 검증 완료로 건너뛰기 실행을 만들지 않는다.

## 배포 시간 최적화

검증에서 생성한 immutable 패키지를 한 번 보관하고 배포 단계에서 그대로 사용한다. 배포 Action과 서버에서 다시 `npm ci`, Gradle 검사·컴파일, Vite 빌드를 수행하지 않는다. 검증된 run·Git SHA·릴리스 ID·archive SHA와 대상 환경을 확인하고, 선택한 artifact의 manifest를 다시 확인한 뒤 전환한다. 빌드 캐시는 성능을 위한 자료이며 배포 근거는 artifact다.

lockfile·도구 버전에 맞는 npm/Gradle 캐시를 유지한다. Gradle 빌드 캐시는 `gradle/actions/setup-gradle`이 매 실행 뒤 저장하며, Kotlin 입력이 같은 다음 실행에서 detekt·compileKotlin·test를 FROM-CACHE로 재사용한다. 캐시는 같은 브랜치와 기본 브랜치의 항목만 읽을 수 있으므로 Kotlin을 바꾼 PR의 첫 실행과 병합 직후 기본 브랜치 실행은 전체 컴파일을 수행한다. 오래된 배포가 새 배포를 덮지 않도록 환경별 배포를 직렬화하며, 서비스 전환 중인 배포를 새 PR 때문에 강제 취소하지 않는다. 승인된 TEST 배포가 현재 활성 후보와 같으면 변경 없이 종료한다. 전송·검증·백업·전환·health 확인의 실제 소요 시간을 남겨 병목을 줄인다. 실패 시 검토된 rollback을 사용하고, 배포 속도를 위해 자료 백업·단일 writer·활성 릴리스 비교를 생략하지 않는다.

## 완료 보고

커밋 접두사·SHA, PR, CI 실행과 결과, 실제 배포 릴리스와 확인한 화면을 구분한다. 배포 후 달력·메뉴·자료를 인증된 화면에서 확인하고 임시 접근 자료를 정리한다. 로컬 빌드 성공을 배포 성공으로 표현하지 않는다.
