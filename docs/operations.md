## 관제 우측 카드

- 배송지 상세: 주소, 박스, ETA, 고객 요청, 배송팁. 이력·알림 보기로 해당 배송지의 배송 관리에 진입합니다.
- 배송 관리: 선택 배송지의 처리 이력/고객 알림을 시간순 조회하고 유형별 필터와 안내 작성을 제공합니다. 대상 없는 차량 사건은 별도 접힌 영역에 있습니다.
- 배송 순서 관리: 버튼으로 즉시 순서 편집 상태를 엽니다. 추가 편집 클릭은 필요하지 않습니다. 보류/복원은 기존 관리 기능으로 유지합니다. 취소는 미저장 변경을 버리고 이력 화면으로 돌아갑니다. 초기화는 미저장 변경만 지우고 편집 화면에 남습니다. 저장 후에도 편집 화면을 유지하며 마지막 저장 순서를 새 기준으로 삼습니다. 저장/취소와 진행 상태 변경 시 오래된 초안 거부는 그대로 적용됩니다.

## 초대 발급

SSH/서버 권한을 가진 운영자가 실행합니다. 공개 관리자 API는 없습니다.

```sh
sudo -u meatbox-demo node /opt/meatbox-demo/current/scripts/manage-access.js issue-invite \
  --file /var/lib/meatbox-demo/access.json \
  --output /var/lib/meatbox-demo/invite-reviewer.txt --hours 24
```

출력은 초대 코드가 담긴 파일 경로뿐입니다. 초대 코드와 `https://3.36.96.156/dev/register`를 검토자에게 별도로 전달합니다. 초대 파일은 0600으로 생성되며 이미 있는 파일을 덮어쓰지 않습니다. 비밀번호는 가입자가 직접 입력합니다. 파일 내용/초대 코드를 로그, 이슈, Git에 남기지 않습니다.

```sh
sudo -u meatbox-demo node /opt/meatbox-demo/current/scripts/manage-access.js disable-user \
  --file /var/lib/meatbox-demo/access.json --username USERNAME
```

비활성화 후 다음 요청/명령부터 거절하며 이미 열린 WebSocket도 다음 상태 전송 전에 권한을 확인하며, 유효하지 않으면 전송을 중단하고 닫힙니다. 로그인 세션은 8시간이며 재시작 시 모두 만료됩니다. 초대 코드가 없는 가입은 실패합니다. 사용자 이름은 대소문자를 구분하지 않습니다.

계정 파일 갱신은 프로세스 간 잠금과 원자적 rename으로 보호합니다. 프로세스 강제 종료로 `access.json.lock` 디렉터리가 남으면 요청은 안전하게 실패합니다. 앱/CLI 작성 프로세스가 없는지 확인하고 상태를 백업한 뒤 잠금 디렉터리를 제거하여 복구합니다. 살아 있는 작성자의 잠금을 제거하지 않습니다.

## 배포

날짜별 주문 릴리스는 준비된 `manifest.json`, `days/`, `regions.geojson` 및 압축본, `destinations.json`만 별도 데이터 아카이브로 전송합니다. 원본 CSV, 로컬 계정, 쿠키, 실행 상태 백업과 QA 계산기는 포함하지 않습니다. 데이터 아카이브 SHA256을 확인하고 `/opt/meatbox-demo/datasets/<sha256>`에 읽기 전용으로 설치한 뒤 해당 릴리스의 `.runtime/dispatch-data`에서 연결합니다. 앱과 데이터 연결을 함께 전환하므로 이전 릴리스로 롤백하면 이전 데이터 연결도 복원됩니다. 원본 데이터 파일을 정적 공개 경로에 두지 않습니다.

배차 계산은 가까운 배송지·제공 세부권역의 공동 배정과 박스 수 균형을 사용합니다. 계산안과 전체 배차 전송은 분리하며, 확정 전에는 배송원 운행으로 표시하지 않습니다. 2026-09-16 발표 명단은 기록 기반 80명입니다. 운영 반영 결과와 실행 SHA는 `vehicle-operations-redesign-plan.md`의 39절에 기록합니다.

### 배차 상태 저장

`DISPATCH_STATE_DIR=/var/lib/meatbox-demo/dispatch-state`를 설정하면 날짜별 배차 체크포인트를 릴리스 밖에 저장합니다. 디렉터리는 서비스 사용자 소유 0700, 파일은 0600입니다. 이 저장소는 애플리케이션의 JSON 체크포인트이며 외부 DB 연결이 아닙니다. 주문 자료·계정·사진 파일과 분리합니다. 환경 변수가 없으면 기존 메모리 동작을 유지합니다.

명령은 체크포인트의 원자적 저장이 성공한 뒤에만 성공 처리하며, 저장 실패 시 이전 상태와 revision을 유지합니다. 재시작 시 날짜·원자료 식별자와 저장 내용의 유효성을 확인하고 복원합니다. 잘못된 저장 파일을 무시하여 배차 전으로 되돌리지 않습니다. 복원에 실패하면 저장 파일과 현재 데이터 해시를 보존한 채 원인을 확인합니다.

파일 내용을 동기화한 뒤 원자적으로 이름을 교체하는 지점을 커밋 경계로 사용합니다. 이는 프로세스·서비스 재시작 복원을 제공하며, 전원 손실이나 파일시스템 장애에서 마지막 디렉터리 갱신까지 보존하는 DB 수준 내구성은 보장하지 않습니다. 단일 서비스 프로세스에서 날짜별 요청을 직렬화하고, 저장 중인 날짜를 메모리 캐시에서 퇴출하지 않습니다. 다중 작성 프로세스나 복제 DB가 필요한 경우 저장 계층을 교체해야 합니다.

배포 전에 저장 디렉터리와 계정 파일을 백업합니다. 새 릴리스의 체크포인트 계약이 호환되는지 확인한 후 교체하며, 구버전 롤백에서도 `DISPATCH_STATE_DIR` 지원 여부를 확인합니다. 저장 기능이 없던 릴리스로 돌아가면 파일은 남아도 화면이 이를 읽지 못하므로, 쓰기를 재개하기 전에 복원 호환성을 해결해야 합니다. 외부 기사 수신·수락과 사진 영구 저장은 별도입니다.

1. 로컬 Node.js 22 환경에서 `npm ci`, 순차 전체 테스트(`npm test -- --test-concurrency=1`, 이 후보는 436건), 구문 검사와 브라우저 검증을 완료하고 커밋합니다.
2. `git archive <sha>`의 내용을 새 릴리스 디렉터리에 풀고 `npm ci --omit=dev`를 실행합니다. 소형 운영 서버에서는 전체 테스트를 다시 실행하지 않고, 릴리스 SHA·의존성 설치·서비스 복원과 아래의 인증/헬스 스모크를 확인합니다.
3. `/opt/meatbox-demo/current`를 새 릴리스로 원자적으로 교체하고 서비스를 재시작합니다.
4. `systemctl is-active meatbox-gateway`, `/login` 200, 익명 `/` 302, `/api/session` 401, 익명 WebSocket 거부를 확인합니다.
5. 로그인 후 운영 화면과 고객·배송원 직행 링크, 시나리오→합본 상태 반영, 로그아웃을 실제 브라우저에서 확인합니다.

다차량 운영 릴리스는 위 절차에 다음 확인을 추가합니다.

- 준비 전과 활성화 직전에 현재 `REVISION`이 예상 이전 SHA인지 각각 확인합니다. 다른 배포가 먼저 반영되었으면 활성화를 중단합니다.
- 새 릴리스 테스트에서 현재 예시 데이터(차량 130대, 배송지 4,523곳, 9,090박스), 다른 크기의 수신 데이터, 배차 화면에서 주문 시나리오 미리보기가 제거됐는지와 고객 지연 알림의 29분, 30분, 31분 경계값을 확인합니다. V1은 8곳/60박스, V2부터 V130은 차량별 35곳/계획 70박스이며 합성 차량의 `capacityBoxes`는 `null`입니다. 예시 수량을 실데이터 계약이나 적재 상한으로 확정하지 않습니다.
- 누적 알림 부하 테스트에서 정차지별 최근 50건과 전체 최근 1,000건 상한, 단조 증가 ID, 배송지별 격리와 사용자 단위 명령 제한을 확인합니다.
- 계정 파일 `/var/lib/meatbox-demo/access.json`은 릴리스 밖에 유지하고, 배포 전후 digest가 같은지 확인합니다.
- 서비스 재시작 뒤 인증된 HTTPS 화면에서 배차 관리, 지도 기반 배송 관제, 자원 관리 세 탭, 고객·배송원 직행 링크, 배송원 금일 배차/근무 이력/사진 확인과 고객 알림을 확인합니다.
- 고객 알림과 배송팁은 시연 메모리에만 기록됩니다. 실제 앱 푸시, 알림톡 또는 배송원 장치 전송을 배포 성공 조건으로 주장하지 않습니다.
- 임시 QA 계정을 사용했다면 확인 뒤 비활성화하고 초대 파일, 쿠키와 작업용 SSH 키를 정리합니다.
- 계정 생성·비활성화 CLI는 `sudo -u meatbox-demo`로 실행합니다. 계정 파일을 원자적으로 교체하므로 root로 실행하면 서비스가 읽지 못하는 root 소유 파일이 생길 수 있습니다. 파일 소유자 `meatbox-demo:meatbox-demo`와 권한 `0600`을 확인합니다.

세부 기능 경계와 검증 항목은 [다차량 운영 계획](fleet-operations-plan.md)과 [테스트 명세](fleet-operations-test-spec.md)를 따릅니다.

릴리스마다 Git SHA를 파일 `REVISION`에 기록합니다. 로그에는 요청 본문, 비밀번호, 쿠키를 기록하지 않습니다. 서비스는 데이터 디렉터리만 쓸 수 있으며 외부에서는 Node 포트에 접근하지 않고 Caddy HTTPS를 경유합니다.

## HTTPS와 SSLip

최종 Caddyfile에는 Public IP만 있습니다. HTTP는 같은 IP의 HTTPS로 자동 이동합니다. SSLip DNS 자체는 제3자 서비스라 삭제할 수 없지만 이 서비스의 SSLip 호스트와 리디렉션 설정은 제거합니다.

IP 인증서는 160시간 유효하며 Caddy가 자동 갱신합니다. `/var/lib/caddy/.local/share/caddy`를 영속 보존하고 80/443을 유지합니다. 별도 Certbot을 중복 실행하지 않습니다.

IP 주소로 접속하는 클라이언트는 SNI를 생략할 수 있습니다. EC2의 내부 주소와 Public IP가 다르므로 `default_sni 3.36.96.156`으로 올바른 IP 인증서를 선택합니다. 인증서 검증은 끄지 않습니다.

```sh
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
curl -I https://3.36.96.156/login
openssl s_client -connect 3.36.96.156:443 -verify_return_error </dev/null 2>/dev/null \
  | openssl x509 -noout -issuer -dates -ext subjectAltName
sudo journalctl -u caddy --since '1 hour ago' --no-pager
```

공식 근거: [Caddy ACME issuer](https://caddyserver.com/docs/caddyfile/directives/tls), [Caddy 자동 HTTPS](https://caddyserver.com/docs/automatic-https), [Let’s Encrypt IP 인증서](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability).

## 롤백

이전 **인증된** 릴리스로 current 심볼릭 링크를 되돌리고 `meatbox-gateway`를 재시작합니다. 계정 파일은 릴리스 밖에 두어 유지합니다. 최초 전환 이전 서버에는 인증이 없으므로 이전 Caddyfile을 그대로 복원하여 공개하지 않습니다. 첫 릴리스가 실패하면 외부에는 유지보수 503을 내고, 백업은 로컬 확인/복구용으로만 사용합니다.

## 레이아웃 규칙

좌측 메뉴는 **배차 관리 → 배송 관제 → 자원 관리** 순서입니다. 모든 지도는 같은 로컬 MapLibre·OFM 테마와 접힌 출처 표기를 사용합니다. 배차·관제 지도는 Command/Control+휠 확대와 안내 가리개를 유지하고, 고객·배송원 폰 지도는 보조 키와 가리개 없이 일반 휠로 확대·축소합니다. 배송원 순서 편집 중 지도 확대 잠금은 유지합니다. 원본 날짜 자료가 준비된 배차 지도는 인증된 `/api/dispatch-data`에서 날짜별 주문과 공통 SHP를 읽습니다. 날짜 자료가 없는 설치만 `/scenario/api/route-data` 시연으로 돌아갑니다. 날짜별 배차 지도는 낮은 배율에서 표시 대상을 고정하며, 확대 시 추가 핀을 선명하게 표시하고 줌 14 이상에서 모든 개별 핀을 표시합니다. 숫자 묶음은 표시하지 않습니다. 전체 주문 데이터와 선택 차량 강조는 유지하고 차량 마커는 표시하지 않습니다. 관제 지도는 선택 차량의 출처가 확인된 위치와 남은 등록 배송지 마커를 표시합니다. 좌표 없는 주문은 위치 미등록 건수로 알리고 확인되지 않은 좌표나 직선 경로를 만들지 않습니다. 배차 관리의 주문 시나리오 미리보기는 제거했습니다.

관제 차량 목록은 주문 수신 순서를 기본으로 하고 남은 배송지와 박스 단위를 사용합니다. 우측 차량 카드에서 배송지 상세를 펼쳐도 현재 운행 요약은 고정됩니다. 지원배차는 원자료 등급이 연결되기 전까지 진입점과 대기 사유만 표시합니다. 자원 관리의 배송원/차량 탭은 당일 배정·완료·잔여·보류와 박스 지표를 보여줍니다. 연결된 당일 주문은 이름·주소·박스로 표시하고 선택 시 해당 배송 관리로 이동합니다. 배송지 탭은 운영일까지 누적된 배송처를 가나다순으로 조회하는 대장입니다. 여러 날짜의 같은 배송지를 합치고 누적 주문·박스·최초/최근 주문일을 표시하며, 당일 순서·ETA·운행 상태와 내부 ID는 노출하지 않습니다. 성향·평가·메인 권역은 `미등록`이며 `driver-profile-candidates.md`의 미배정 후보만 준비했습니다. 배송원 화면은 금일 배차와 별도 날짜별 데모 근무 이력을 구분합니다. 도착한 현재 배송의 사진 선택과 고객 요청 필수 확인 뒤에만 완료 확인을 진행하며 사진은 브라우저 임시 미리보기이고 서버에 저장하지 않습니다.

## 수동 상태 선택 기준

가이드는 시간순 설명서 대신 주문과 배송 장면을 직접 고르는 여섯 개의 짧은 버튼을 제공합니다. `주문 관련` 그룹은 `접수 완료`, `피킹 중`, `출고 준비`, `배송 관련` 그룹은 `배송 중`, `배송지 도착`, `배송 완료`입니다.

- `set_scenario`는 `received`, `picking`, `ready`, `shipping`, `arrived`, `completed` 가운데 하나와 선택한 실시간 배송지 `S1`부터 `S8`까지를 받습니다.
- 임의 프리셋을 바로 선택할 수 있으며 중간 이벤트를 기다리지 않습니다. 현재와 다른 선택은 상태를 한 번 계산해 모든 인증 연결에 반영하고, 같은 프리셋과 배송지를 다시 선택하면 계산하거나 재전파하지 않습니다.
- 현재 선택은 스냅샷의 `scenarioPreset`과 `scenarioStopId`를 따릅니다. 초기화 값은 `received`와 `S1`이며, 순서 변경이나 보류로 현재 프리셋 의미가 깨지면 두 값이 `null`일 수 있습니다.
- 합성 차량 배송지는 시나리오를 변경하지 않습니다. 배송팁과 운영자 수동 안내는 프리셋 변경으로 삭제하지 않습니다.
- 프리셋과 배송 순서 변경은 고객 약속 시간대와 운영 정확 ETA 기준을 전체 초기화하지 않습니다. 도착과 완료 프리셋은 선택 배송의 고정 실제 도착 시각을 정확 시각으로 제공하고, 약속이 없는 배송만 새 시간대를 만듭니다. 전체 기준 초기화는 명시적 `reset`에서만 수행합니다.
- 서버의 500ms 시뮬레이션 진행은 사용하지 않습니다. 현재 합본의 `OperatingSimulation` 도착은 반복 `tick` 없이 한 번 전환합니다. 일반 시뮬레이션 폴백의 최대 10,000회 안전 제한은 원본 회귀용으로 유지합니다. 자동 주행, 자동 하차 완료, 배속, 사고와 정차 지연 컨트롤도 합본에 없습니다.
- 이전 `advance`, `place_order`, `speed`, `traffic`, `dwell` WebSocket 명령은 차단합니다. 배송원 화면의 기존 `arrive_stop`은 수동 `arrived` 프리셋을 한 번 적용합니다. `complete_stop`은 도착한 현재 배송에서 사진 선택과 고객 요청 필수 확인을 거친 확인 버튼으로만 보내며 수동 `completed` 프리셋을 한 번 적용합니다. 사진 파일은 명령에 포함하거나 서버에 저장하지 않습니다.
- 인증 상태 확인, 사용자 명령 제한 정리와 브라우저 WebSocket 재연결에 필요한 타이머는 유지합니다.
- 인증 후 `/`는 `/combined/`로 바로 이동합니다. `/scenario/`는 상현 원본 고객 화면으로 진입하고, `/scenario/customer`, `/scenario/driver`, `/scenario/control`, `/scenario/present`는 각 원본 참조 화면을 제공합니다. 원본 파일은 수정하지 않으며 별도 타이머나 자동 진행 엔진을 시작하지 않습니다.
- 상세 계약과 로컬 검증은 [수동 시나리오 계획](manual-scenarios-plan.md)과 [테스트 명세](manual-scenarios-test-spec.md)를 따릅니다. 이번 개편의 완료는 로컬 검증으로 판단하고 배포가 별도 요청되면 릴리스 SHA, 운영 서비스 상태와 인증된 화면을 추가로 확인합니다. 운영 계정 변경은 기능 변경 범위에 포함하지 않습니다.


## 가입과 로그인 입력

비밀번호 최소 길이는 데모 사용성에 대한 사용자 결정으로 8자, 최대 128자입니다. 길이 조건은 브라우저와 서버가 함께 검증합니다. 실제 업무용 인증 표준 준수를 의미하지 않습니다.

필드마다 안내 영역을 하나만 두고, 오류가 생기면 같은 위치의 문구를 해결 방법으로 교체합니다. 수정하면 원래 안내를 복원합니다. 한 줄 높이를 확보하고 긴 문구는 잘리지 않게 줄바꿈합니다. 색 외에도 오류 문구, `aria-invalid`, 연결된 안내와 제출 시 포커스로 상태를 전달합니다.

참고: [GOV.UK 오류 문구](https://design-system.service.gov.uk/components/error-message/), [W3C 폼 알림](https://www.w3.org/WAI/tutorials/forms/notifications/). 2026-09-13 확인.

## 시간 및 요청 확인 후속 계약 (2026-09-15)

- 기존 이동·하차 입력이 있는 V1만 최종 인도 완료와 잔여 시간을 계산합니다. 마지막 도착 ETA와 최종 하차 완료를 구분하며 보류·결측은 완료 미확인입니다. 전체 기간은 가장 이른 고정 출발부터 가장 늦은 최종 완료까지, 계산 가능한 차량 수와 함께 표시합니다. 실제 GPS 기반 지원배차 판단값으로 사용하지 않습니다.
- `customerRequests`는 예시 출처와 배송지별 요청 ID/종류/문구/필수 여부를 담습니다. null은 미수신, 빈 items는 요청 없음입니다. 사진 후 모든 필수 항목을 체크해야 `complete_stop`에 `stopId`와 `confirmedRequestIds`를 보냅니다. 서버는 현재 도착 배송지의 정확한 확인 목록만 허용합니다. 사진 자체는 서버 증빙이 아닙니다.
- 보존 참조 화면 `/scenario/driver`의 완료 버튼은 합본 배송원 화면으로 안내합니다. 원본 파일을 수정하거나 필수 요청 검사를 우회하지 않습니다. 수동 `completed` 시나리오는 별도 데모 전환으로 유지합니다.

### 리모컨의 다음 배송지

`다음 배송지`는 현재 V1 배차 순서의 다음 대상을 해당 뷰어에서 선택합니다. 이후 기존 상태 버튼으로 장면을 선택합니다. 자동 재생이나 완료 처리를 실행하지 않으며 마지막 항목은 `마지막 배송지`로 비활성화됩니다.

### 배송원 요청 아이콘

배송원 현재 배송지에는 냉장고 보관, 문 앞, 실내, 직접 전달 아이콘만 표시하고 상세/촬영 후 확인에는 요청 문구와 필수 체크를 표시합니다. 배송원 화면의 예시 배지는 생략하며 관제와 source 메타데이터에는 예시 출처를 유지합니다. S6는 `indoor`(매장 안에 두기) 시연이며 완료 시 `S6-indoor` 확인이 필요합니다.

각 요청 아이콘을 누르면 해당 요청 한 항목의 내용이 배송원 팝업으로 열립니다. 열람은 이행 확인이나 배송 완료가 아니며 필수 체크는 사진 후 확인 단계에서 진행합니다.

## 원본 날짜 자료와 수동 배차 (2026-09-16)

과거 자료 기준일 2026-09-16과 335개 날짜별 산출물 준비/교체 명령, 원본 중복 합산 및 좌표 기준은 [날짜별 배차 자료](dated-dispatch-data.md)를 따릅니다. `DISPATCH_DATA_DIR` 기본값은 무시되는 `.runtime/dispatch-data`입니다. 새 원본의 외부 업로드·배포는 이번 작업에 포함하지 않습니다.

CSV 기사 표기는 후보 배송원 자료입니다. 새 현재·미래 날짜는 미배차로 시작하며, 배송 가능 인원을 선택하고 계산안을 검토한 뒤 전체 배차 전송으로 확정합니다. 핀배차는 계산안에서 같은 이름·주소의 주문을 함께 옮깁니다. 전송 전 배송원 운행 목록은 비어 있고 고객은 배차 대기로 조회합니다. 기준 오늘은 `Asia/Seoul`의 실제 달력 날짜이며 과거 날짜 변경은 UI와 서버에서 거부합니다. 기존 진행·완료 주문과 사건은 보존합니다. 차량번호·수도권 위치의 생성 출처는 내부 메타데이터에 남기며 실제 GPS로 사용하지 않습니다. 날짜별 상태는 서버 프로세스에서 공유하며, `DISPATCH_STATE_DIR` 설정 시 위의 날짜별 체크포인트를 파일에 저장합니다. 계산 기준과 확정 후 배정 변경 규칙은 결정 대기 중입니다. 외부 기사 앱 전달·수락도 연결되지 않았습니다.

실제 주문의 시나리오/도착/사진 후 완료/순서/보류/배송 팁/고객 알림은 로컬 시연입니다. 원본 날짜의 과거 실시간 이력으로 주장하지 않습니다. 근무 이력은 원본의 날짜별 기사 배정 자료를 조회하며 가상의 근무 시간과 상품/고객 요청을 삽입하지 않습니다. 상태 및 명령 API와 결측 처리는 [날짜별 배차 자료](dated-dispatch-data.md)를 참조합니다.

운영용 산출물은 2025-09-17 자료를 2026-09-16에 맞춰 전체 날짜를 364일 이동합니다. 요일을 보존하며 원래 날짜는 `sourceDate`로 기록합니다. 화면의 운영일과 관제·근무 이력 API 날짜가 같은 기준을 사용합니다. 기존 원본 날짜 산출물은 `.runtime/dispatch-data-source-dates`에 보존합니다.
