# 첫 프런트 포크 작업

2026-10-05, Asia/Seoul. 기준 소스는 `main`의 `c1f29a6`이다. 기존 환경 설정의 미커밋 작업을 보존한다. 사용자 승인에 따라 탐색 → 계획 → 적용 → 검토를 진행하며, 당분간 테스트 서버 한 대만 사용한다.

## 작업 단위

- 요구 동작: 기존 운영·기사·고객·로그인·등록·시나리오·디자인 참조 UI를 `apps/web` 한 패키지에서 빌드하고 기존 Node API와 연결해 사용한다.
- 변경 범위: `apps/web`, 루트 개발 명령과 관련 작업 문서. 기존 서버·업무 라이브러리·원본 UI·실자료·원격 배포는 변경하지 않는다.
- 상태 소유자: 기존 Node API가 날짜별 배차·운행 집계, 별도 자원 revision, 계정·세션과 레거시 시뮬레이션을 계속 소유한다. Kotlin은 아직 health 도구 검증 단계다.
- 완료 조건: 새 프런트가 원본 UI 소스에 의존하지 않고 빌드된다. 새 코드·포크된 모델을 검사하고, 인증·Origin·보호 자산·WebSocket·날짜 배차·기사/고객 상태를 격리된 자료로 검증한다.
- 한계: 로컬 검증은 테스트 서버 배포, SaaS 인가, 실제 주문·GPS·증빙·알림 구현 완료를 뜻하지 않는다. 원본 삭제와 Node 종료는 별도 게이트다.

| --- | --- |
| `apps/combined` | 통합 HTML 3개, 브라우저 모듈 45개, 모델 테스트 36개, CSS 16개, 지도·폰트·브랜드·worker 자산 |

| `workspaces/jiin-ui` | 디자인 참조 HTML·브라우저 모듈·CSS·합성 예제·모델 테스트 |

날짜별 REST 상태와 레거시 WS 시뮬레이션은 서로 다른 상태다. CSV/JSON 원본은 실제 공급자 계약을 대신하지 않는다. 로그인은 내부 검토자 기준이며 역할·차량·고객별 서버 인가는 아직 없다.

## 적용 순서

1. 원본 경로·SHA-256·이관 결과를 기록하고 UI를 포크한다. 기존 화면의 내부 배치를 유지하며 runtime 문자열·worker·지도·폰트가 쓰는 고정 자산 경로를 보존한다.
2. 원본 서버의 HTML·JS 응답 변환을 새 프런트 파일에 반영한다. classic JS와 외부 라이브러리의 산출 누락을 막고 라이선스를 함께 보존한다.
3. 로그인·등록 화면은 프런트가 소유한다. 기존 인증 POST의 redirect/cookie와 오류 의미를 연결하되 서버 응답 HTML을 새 페이지로 그대로 주입하지 않는다.
4. Vite 다중 HTML 빌드를 설정한다. 보호 화면·자산과 API·WS를 검사하는 loopback 전용 로컬 이행 게이트웨이로 빌드 결과를 검증한다. 기존 Node가 유일한 업무 writer이며 Cookie·Origin을 그대로 전달한다.
5. 순수 모델 테스트는 포크된 코드로 이전한다. 기존 서버·scenario 데이터에 의존하는 테스트는 프런트 자체 테스트와 API 이행 테스트로 분리하며 서버 구현을 프런트에 복사하지 않는다.
6. 소스·회귀·lint·typecheck·빌드·실제 브라우저 검증을 수행한다. 결과와 확인하지 못한 범위를 아래에 기록한다.

## 이행 연결의 고정 계약

- 로컬 브라우저는 이행 게이트웨이 origin에 접속한다. 기존 Node는 별도 loopback 포트에서 실행하고 `PUBLIC_ORIGIN`은 브라우저의 정확한 origin으로 설정한다. Cookie·Origin·Set-Cookie·응답 상태·Location·WebSocket handshake를 그대로 전달한다.
- 공개 범위는 로그인·등록 HTML과 정확한 portal 자산, 독립된 인증 번들뿐이다. 인증 번들은 보호 UI 코드를 import하지 않는다. 공용 번들이 생기면 공개/보호 코드가 섞이지 않는지 산출물에서 검증하고 공개 allowlist를 확정한다. 나머지 UI·JS·CSS·지도·worker는 서버 세션 확인 후 제공한다. 세션 확인의 정상 401은 보호 페이지를 로그인으로 이동시키고 API 401은 그대로 전달한다. Node 연결 실패·timeout·5xx·해석 불가능 응답은 503으로 닫힌다.
- 인증 POST의 실패는 400·401·403·429 및 서버/통신 오류로 구분한다. HTML 응답에서는 `.error`와 `aria-invalid` 입력에 연결된 정해진 피드백 요소의 `textContent`만 추출한다. 원문 DOM·응답 입력값·비밀번호·초대 코드를 주입하거나 다시 출력하지 않는다. 성공은 쿠키와 안전한 same-origin redirect를 따른다.
- 서버의 prefix·Leaflet SRI·숨김 스타일·인증 script·WS 및 원본 주소·기사 증빙 링크·UI 제목·308 alias/query 계약을 포크된 파일과 실제 dist HTTP 응답에서 확인한다. CSP·nosniff·frame deny·referrer 정책도 새 응답에서 검사한다.
- 자체 UI 회귀 34개는 새 프런트만 사용한다. 서버에 의존하는 회귀 5개는 별도 `test/web-fork-legacy`에서 기존 writer의 상태를 새 UI 모델에 연결한다. 원본/대상 SHA-256와 변환 이유를 기록해 무변경 모델의 동등성과 허용된 자산 경로 변환을 확인한다. 기존 기준선 93개 외 새 모델·산출물·게이트웨이 검증까지 통과해야 첫 적용을 완료한다.

## 검증 기준

- 기존 회귀: 게이트웨이, 계정, 날짜별 명령, 자원 CAS, 시스템 통합과 핵심 UI 모델 테스트를 먼저 실행해 기준 동작을 확인한다.
- 포크 자체: 원본 목록 누락, 로컬 자산·import 의존성, Node-only 브라우저 import, 공개 산출물의 서버·테스트·비밀 파일 노출을 검사한다.
- 인증 연결: 공개 portal 자산만 허용, 보호 UI·자산은 서버 세션으로 검사, 잘못된 Origin·세션·WS 경로는 거절, API 장애는 fail closed, next의 외부 redirect 금지.
- API·상태: 합성 날짜 자료로 계산안 → 확정 → 기사·고객 공유 상태, 과거 읽기 전용·revision 충돌·체크포인트 재시작을 확인한다. 자원 revision은 날짜 revision과 별개다.
- 브라우저: 로그인·등록, 운영 메뉴, 기사·고객 직접 링크, 시나리오·가이드를 확인한다. 지도 외부 타일 통신과 실제 기기·공급자 연결 증거는 별도로 기록한다.
- 변경 위험: 실자료와 기존 체크포인트를 읽거나 수정하지 않는다. 원본 UI 소스·실행 산출물·별도 Push 시범 서비스는 보존한다.

## 첫 포크 당시 결과

첫 프런트 포크의 탐색·계획·적용·검토를 완료했다. 원본 142개 파일을 대조해 포털의 두 HTML 변환과 폰트·브랜드 별칭을 포함한 대상 145개를 `apps/web/fork-inventory.json`에 기록했다. 원본 리비전과 SHA-256, 대상 SHA-256, 변환 이유를 고정했다. 순수 모델 테스트 34개는 새 프런트에서 실행하며, 기존 writer에 의존하는 테스트 5개는 루트에 분리했다. 원본 서버·업무 라이브러리·원본 UI·배포 파일은 수정하지 않았다.

검증 결과:

- `make check-new-stack`: Kotlin 컴파일·detekt·테스트·JAR, 프런트 strict TS·lint·빌드, 프런트 테스트 250개, 실제 dist 검사 3개, 원본 대응/기존 writer 연결 검사 36개 통과.
- `npm test`: 기존 서버·원본 화면과 포크 연결 회귀 488개 통과. Kotlin HTML 보고서가 Node 테스트로 자동 실행되는 충돌을 확인해 루트 `package.json`의 테스트 경로를 명시했다. 새 프런트 자체 검사는 별도로 실행한다.
- Oxlint 오류 0개. 기존 `source-viewer-plan.mjs`, `driver-history.mjs`의 Anti Slop 경고 2개는 기록하고 유지했다. 기존 JS/MJS는 `checkJs: false`이며 전체 strict 타입 검사를 했다고 판단하지 않는다.
- 독립 코드 검토에서 API 본문 중단 처리와 로그인된 계정의 등록 redirect 문제를 수정하고 회귀 검사를 추가했다. 수정 후 인증·게이트웨이·실제 산출물 18개 검사를 다시 통과했으며 추가 조치 항목은 없었다.
- 실제 브라우저: 로그인 입력 오류는 POST 없이 표시, 잘못된 계정은 페이지 안에서 오류 표시, 정상 로그인과 자원 2대 표시, 주문 3건·9박스 계산안→확정, 기사 출발→관제 이력→고객 배송 중 상태 반영을 확인했다. 과거 날짜는 읽기 전용으로 조작 버튼이 비활성화됐다.
- 고객 화면의 390px 뷰포트에서 문서 가로 넘침이 없었다. 지도·폰트가 표시됐고 확인한 운영·기사·고객·시나리오·참조 화면의 console 오류/경고는 없었다. 등록 필수값 누락은 POST 0건으로 차단됐다. 등록 성공, 로그아웃 API, WebSocket의 세션·Origin 계약은 자동 검사로 확인했다.

`make run-fork-fixture`로 임시 디렉터리에 합성 주문·계정·상태·자원 DB를 만들고 새 프런트와 기존 Node writer를 함께 실행할 수 있다. 검증 자료는 실제 주문·계정·체크포인트와 분리되며 종료 시 삭제된다. 검증 이미지는 Git 제외 경로 `apps/web/.runtime/proof/`에 저장했다.

남은 범위: 테스트 서버 배포·기존 배포 라인 전환은 수행하지 않았다. Kotlin 업무 API·저장소·SaaS 사용자별 인가와 실제 주문·GPS·사진·알림 계약은 다음 작업이다. 기사 화면의 기존 ‘로그아웃’은 포털 안내를 표시하는 검토 UI이며 실제 계정 종료 UI로 개선되지 않았다. 시나리오·가이드의 예제와 데모 문구도 보존했다. 이 첫 포크를 제품 정리 또는 운영 준비 완료로 판단하지 않는다. 원본 UI 삭제와 Node 종료 조건은 아직 충족되지 않았다.

## 후속 디자인·구조 개선

위 수치는 최초 포크 검증 시점의 기록이다. 현재 프런트는 [디자인·구조 개선](frontend-design-cleanup-plan.md)을 거쳐 공유 theme·책임별 CSS·공통 지도·현행 가이드를 적용했다. 인벤토리 schema 2는 최초 대상 145건을 보존하면서 현재 파생 163건·authored 17개를 구분한다. 최신 검사·브라우저 결과와 의도한 참조 차이는 후속 문서에 둔다.
