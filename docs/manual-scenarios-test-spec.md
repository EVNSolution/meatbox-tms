# 수동 시나리오 테스트 명세

## 자동 테스트

### 명령 검증과 대상

- 인증된 같은 Origin WebSocket에서 `received`, `picking`, `ready`, `shipping`, `arrived`, `completed`와 `S1`부터 `S8`까지의 조합만 허용한다.
- 알 수 없는 프리셋, 누락되거나 합성인 `stopId`, 문자열이 아닌 필드는 상태를 바꾸지 않는다.
- 같은 사용자의 여러 연결에 적용되는 이동식 1초 10개 명령 제한과 11번째 송신 연결의 `4429` 종료를 유지한다.

### 수동 전환

- `주문 관련`의 `접수 완료`, `피킹 중`, `출고 준비`와 `배송 관련`의 `배송 중`, `배송지 도착`, `배송 완료`는 앞선 단계의 대기 이벤트 없이 임의 순서로 선택할 수 있다.
- 현재와 다른 유효한 프리셋 한 번은 서버 상태 계산과 브로드캐스트를 한 번만 발생시킨다. 같은 `scenario`와 `stopId`를 다시 보내면 계산과 브로드캐스트가 없다.
- `arrived`는 선택한 V1 배송지에 실제 도착을 기록하고, `completed`는 같은 배송지의 도착과 완료를 일관되게 기록한다.
- 같은 프리셋을 다시 선택해도 자동 진행 루프를 시작하거나 시간이 계속 흐르지 않는다.
- 프리셋 전환 전 작성한 배송팁과 `manual` 고객 안내는 전환 뒤에도 남는다.
- 합성 배송지를 선택하면 시나리오 명령을 보내지 않으며 V1 상태도 바뀌지 않는다.
- 스냅샷의 `scenarioPreset`과 `scenarioStopId`는 현재 선택을 나타낸다. 초기화하면 `received`와 `S1`이고, 프리셋 의미를 깨는 배송 순서 변경, CAS 저장이나 보류 뒤에는 둘 다 `null`일 수 있다.
- 배송원 화면의 기존 `arrive_stop`, `complete_stop` 명령은 각각 `arrived`, `completed` 프리셋을 한 번 적용한다.
- 배송 순서 변경 뒤 프리셋을 선택하거나 `shipping`에서 `arrived`, `completed`로 전환해도 기존 고객 약속 시간대가 유지된다.
- `arrived`와 `completed` 스냅샷은 선택 배송의 고정 실제 도착 시각을 운영 정확 시각으로 제공한다. 기존 고객 약속이 없을 때만 해당 시각을 기준으로 시간대를 최초 생성한다.
- 명시적 `reset`은 고객 약속과 운영 정확 ETA 기준을 새로 만들지만 다른 프리셋과 순서 변경은 이를 전체 초기화하지 않는다.

### 타이머 제거와 회귀

- 서버를 명령 없이 두어도 시뮬레이션 시각, 차량 진행과 배송 상태가 500ms 단위로 변하지 않는다.
- 현재 `OperatingSimulation`의 `arrive_stop`은 `tick(true)` 반복 없이 `arrived`를 한 번 적용하고, `complete_stop`은 `completed`를 한 번 적용한다. 일반 시뮬레이션 폴백의 최대 10,000회 안전 제한은 그대로 회귀 검증한다.
- 이전 `advance`, `place_order`, `speed`, `traffic`, `dwell` WebSocket 명령은 거절하고 상태를 바꾸지 않는다.
- 인증·세션 확인, 명령 제한 정리와 브라우저 WebSocket 재연결 타이머는 계속 작동한다.
- Origin·세션 검증, 알림 정차지별 50건과 전체 1,000건 상한, 배송 순서 CAS, 고객 ETA 앞뒤 30분 시간대와 30분 초과 지연 정책을 유지한다.
- `workspaces/jiin-ui/`, `workspaces/sanghyun-scenario/`와 원본 스냅샷 해시는 바뀌지 않는다.
- `/scenario/` 화면 요청은 합본 화면으로 이동하고, route data와 공용 정적 자산 요청은 계속 정상 응답한다.

### 지도 시나리오

- 주문 관리 본문에는 상시 노출된 박스 수 편집기가 없고 지도 모서리의 `지도 시나리오` 버튼으로 설정 팝업을 연다.
- 목표 물량은 80%, 100%, 120% 경계를 포함한 범위에서 수동 선택하며 기본값과 초기화 값은 100%다.
- 100% 기준은 수신한 전체 배송의 박스 합계다. 차량 수와 배송지 수는 수신 데이터 길이에서 읽으며 60박스당 필요 차량 같은 추정값을 만들지 않는다.
- 범위를 벗어난 값과 숫자가 아닌 값은 화면의 정의된 범위로 정규화되고 가로 넘침이나 입력 손실을 만들지 않는다.
- 목표 물량을 바꿔도 WebSocket 명령을 보내지 않고 원본 스냅샷, 개별 주문 박스 수, 차량·배송지 수, ETA, 알림, 팁과 배송 순서가 바뀌지 않는다.
- 기준값 누락은 `미확인`으로 구분하고 명시적인 빈 배열이나 합계 0은 0으로 표시한다.
- 모든 비율에서 지도는 원본 주문 마커와 원본 박스 수를 표시하고 차량 위치 계층을 만들지 않는다.
- 지도는 빈 배경과 주문 표본을 유지하며 실제 좌표, 권역이나 배차 결과로 표시하지 않는다.
- 설정은 자동으로 증가하지 않고 마지막 수동 선택 값에 머문다.

## 브라우저 검증

### 1280px

- 전역 가이드에서 주문 세 버튼과 배송 세 버튼, 현재 선택 상태를 설명서 없이 빠르게 구분한다.
- V1 배송지를 선택하면 여섯 버튼을 임의 순서로 사용할 수 있고 현재 프리셋은 스냅샷 값과 일치한다.
- 같은 활성 버튼을 다시 눌러도 화면 상태와 네트워크 상태 전파가 반복되지 않는다.
- 합성 배송지를 선택하면 변경할 수 없다는 문구와 비활성 상태가 분명하다.
- 주문 관리 본문은 지도가 주 영역을 차지하고 모서리의 `지도 시나리오` 팝업이 지도 내용을 가리지 않는 범위에서 열린다.

### 390px와 320px

- 주문·배송 시나리오 버튼은 44px 이상의 조작 높이와 키보드 포커스를 유지하며 가로 넘침이 없다.
- 지도 시나리오 팝업은 화면 안에 머물고 목표 물량, 100% 복귀, 닫기와 현재 값을 모두 조작할 수 있다.
- 팝업을 닫은 뒤 초점이 `지도 시나리오` 버튼으로 돌아간다.
- 사고, 정차 지연, 자동 주행, 자동 하차 완료와 배속 컨트롤이 화면에 없다.

브라우저 콘솔 오류와 처리되지 않은 Promise rejection이 없어야 한다. 시나리오 전환 중 배송팁 입력과 운영자 안내 작성 내용이 사라지지 않는지 함께 확인한다.

## 로컬 완료 기준

```sh
npm test
node --check server.js
node --check apps/combined/app.mjs
node --check apps/combined/scenario-tools.mjs
node --check apps/combined/order-planning.mjs
git diff --check
```

검증은 변경이 있는 같은 작업 트리에서 실행한다. 이번 작업은 로컬 완료까지만 기록하며 배포 상태나 운영 HTTPS 반영을 완료로 주장하지 않는다.
