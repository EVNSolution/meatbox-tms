# 실서버 데이터 수신 준비와 규모 검증

> **이력·검토 자료.** 아래 내용은 작성 당시의 계획·판정·시험 결과입니다. 수량·구현 상태·배포 여부를 현재 상태로 해석하지 않습니다. 현행 계약과 절차는 [문서 안내](README.md), 후속 전환 조건은 [운영 전환 기준](production-readiness.md)을 사용합니다.

기준일: 2026-09-15. 이번 변경은 전송과 화면 처리의 병목을 줄이고 현재 데모 fixture를 예상 규모에 가깝게 확대한 준비 작업이다. 외부 서버 연결, 실데이터 적재, 운영 인프라 부하 검증은 아직 수행하지 않았다.

## 예상 규모

사용자 기준은 배송원 또는 차량 한 대에 약 70박스, 약 35개 배송지다. 배송지당 평균은 약 2박스다. 이 수치는 부하 예산이며 차량의 최대 적재량, 배송지 상한 또는 주문별 확정 수량이 아니다.

| 부하 표본 | 차량 | 배송지 | 박스 |
|---|---:|---:|---:|
| 현재 차량 수를 사용한 준비 기준 | 130 | 4,550 | 9,100 |
| 두 배 차량 수로 확인한 확장 표본 | 260 | 9,100 | 18,200 |

실제 차량 수와 배송지 수, 상품 및 박스 수는 수신 데이터에서 읽는다. 물량 비교는 그 데이터의 합계를 100%로 두고 80–120%로 유지한다. 9,100박스 예시의 비교 범위는 7,280–10,920박스다. 개별 주문 배분, 차량 수 추정, 배차 알고리즘과 평가 시나리오는 확정하지 않는다.

현재 시연 fixture는 V1의 기존 8곳/60박스를 유지하고 V2부터 V130까지 차량별 35곳/70박스 계획값으로 늘려 전체 130대/4,523곳/9,090박스를 제공한다. 합성 차량의 `capacityBoxes`는 `null`이며 70박스는 상한이 아니다. 별도의 `scripts/capacity-fixture.cjs`는 정확히 130대/4,550곳/9,100박스와 두 배 표본을 재현하는 격리 부하 자료이며 현재 화면 fixture나 실제 배송 데이터가 아니다. 두 표본 모두 좌표와 ETA를 만들지 않는다.

## 반영한 처리 구조

- 합본 운영, 고객, 배송원 뷰어는 `meatbox-state-v2` WebSocket 프로토콜을 사용한다. 첫 연결에는 전체 상태를 받고 이후에는 바뀐 필드와 배송지만 받는다. 기존 뷰어는 전체 상태 형식을 유지한다.
- `fleet.deliveries`는 ID별 추가, 수정, 삭제와 순서 변경을 전송한다. 수량 0과 값 없음, 배송지 삭제, 순서 변경을 구분한다. 배열의 고정 크기나 `S1` 같은 ID 패턴을 전송 계층에 요구하지 않는다.
- 서버는 공용 최신 프레임과 비교 기준만 보관한다. 연결별로 과거 상태를 쌓지 않고 한 번에 한 프레임을 쓴다. 그 사이의 변경은 최신 상태로 합친다. 갱신을 건너뛰었거나 재연결했을 때에는 전체 상태로 복구한다.
- 인증 또는 소켓 쓰기가 10초 안에 끝나지 않는 연결은 종료한다. 클라이언트는 최초 1.5–2.5초 사이에 분산 재연결하고 실패가 반복되면 최대 30–31초까지 대기를 늘린다. 정상 상태를 받은 뒤에는 대기를 초기화한다. 화면이 수신 상태를 거절한 경우도 재연결하여 전체 상태를 다시 받는다. 세션은 연결마다 다시 확인한다. 로그아웃, 세션 만료, 다른 Origin 차단은 유지한다.
- 배송 목록은 전체 데이터를 검색하고 50행씩 표시한다. 검색과 필터 변경은 첫 페이지로 돌아가고, 실시간 갱신은 페이지를 유지하거나 남은 데이터 범위에 맞춘다. 합계는 전체 데이터 기준이다.
- 고객 매장 선택기도 전체 검색과 50개 단위 페이지를 사용한다. 입력 포커스와 검색어, 선택 매장을 유지한다. 운영 화면은 현재 열린 페이지에 필요한 내용만 다시 그린다.

전송량은 줄었지만 서버가 변경을 찾기 위해 상태를 순회하고 직렬화하는 비용, 브라우저의 전체 어댑트 비용은 여전히 존재한다. 차량 목록, 알림, 사건 배열 등 배송지 외 필드는 변경 시 해당 필드 전체를 보낸다. 모든 데이터가 바뀌면 전체 상태에 가까운 비용이 발생한다. 또한 현행 인증은 각 연결에 상태를 보낼 때마다 계정 JSON 파일을 읽으므로 연결 수와 갱신 빈도에 비례한 파일 읽기가 남아 있다. 실서버 인증 연결 시 명시적 세션 무효화와 만료를 유지하는 메모리 검사 또는 인증 저장소로 전환하고 별도로 부하를 검증해야 한다.

## 측정 결과

재실행:

```sh
npm test
npm run check:capacity
npm run check:capacity:stream
# 연결 수를 바꾸는 로컬 진단 예시 (1–500은 진단 도구 자체의 실행 보호 범위)
npm run check:capacity:stream -- 260
```

macOS arm64, Node v26.3.1에서 측정했다. 운영 Node 22와 운영 머신의 측정값으로 취급하지 않는다. 원시 결과는 [capacity-measurements.json](capacity-measurements.json)에 보관했다.

| 합성 배송지 | 전체 최초 프레임 | 배송팁 1곳 수정 시 최대 프레임 | 감소율 | 인코딩 p95 | 복원 p95 | 화면 모델 변환 p95 |
|---:|---:|---:|---:|---:|---:|---:|
| 4,550 | 1,526,982 B | 541 B | 99.96% | 13.72 ms | 2.39 ms | 2.04 ms |
| 9,100 | 3,069,302 B | 541 B | 99.98% | 30.86 ms | 2.17 ms | 2.70 ms |

각 표본에서 서로 다른 배송지 30곳을 순서대로 수정하고, 모든 복원 결과가 원본 전체 상태와 같은지 검증했다. 위 감소율은 배송지 한 곳 수정 사례에 한정된다.

실제 WebSocket 연결 130개를 같은 로컬 프로세스에서 열고, 매번 차량별 한 곳씩 총 130개 배송지를 변경하는 배치를 10회 전송했다. 최초 전체 수신에는 약 1.76초, 후속 배치의 전체 연결 수신에는 약 58–84ms가 걸렸다. 배치별 연결당 프레임은 약 50–51KB였다. 실제 파일 기반 세션 검사와 테스트 계정 한 개를 사용했다. 이 검증은 갱신 정확성과 동시 전송 회귀를 확인한 것으로 운영 SLA가 아니다.

첫 연결 130개에 전체 상태를 보내는 데에는 합계 약 198.5MB가 필요했다. 변경분 전송만으로 최초 동시 접속 비용까지 사라지지는 않는다. 고객/차량별 데이터 구독과 제한된 최초 조회가 실제 서비스 연동에서 필요하다. 기록된 RSS 약 727MiB에는 서버와 130개 테스트 클라이언트가 모두 들어 있으므로 서버 메모리 요구량으로 사용할 수 없다. TLS, 지도 타일, 외부 수신, DB, 이미지와 실제 통신망은 측정에 포함하지 않았다.

브라우저 격리 검증은 4,550곳에서 배송 목록 50행, 목록 끝의 배송지 전체 검색, 갱신 중 페이지/입력 유지, 차량의 35개 배송지 관제, 주문 관리의 9,100박스 기준 표시와 고객 매장 검색을 확인했다. 별도 3044 포트를 사용하며 사용 중인 3003의 시나리오는 초기화하지 않는다.

## 실제 연결 전 확정할 수신 조건

다음은 어댑터 구현의 확인 목록이다. 외부 서버의 API 이름이나 JSON 필드명을 확정한 계약이 아니다.

| 영역 | 필요한 조건 | 수신 시 처리 기준 |
|---|---|---|
| 식별 관계 | 차량, 배송원, 배송지, 주문의 안정된 ID 및 배차 소속 | 정규화한 ID 중복과 존재하지 않는 차량 참조를 거절한다. 배열 위치나 권역명으로 소속을 추정하지 않는다. |
| 수량 | 박스 수의 단위와 상품 수량의 구분, 미확정 수량의 표현 | 0과 미확인을 구분한다. 음수, 비정상 숫자, 필수값 누락을 검증한다. 70박스 또는 35곳을 상한으로 검사하지 않는다. |
| 위치 | 주소 정제 결과, 좌표의 기준과 정확도, 실제 차량 위치 | 좌표가 없으면 없는 상태로 둔다. 주소를 임의 좌표로 바꾸지 않는다. 경로는 실제 도로 경로 데이터가 있을 때만 표시한다. |
| 상태와 시각 | 차량의 현재 목적지, 배송 순서, ETA, 도착, 완료 | 예정 시각과 실제 시각을 분리한다. 이벤트 발생 시각, 시간대, 운영 날짜를 명시한다. |
| 갱신 | 스냅샷 버전, 변경 순서, 중복 이벤트 식별, 삭제/재배차 표현 | 오래된 갱신과 중복 이벤트를 식별한다. 단절 뒤 전체 재수신으로 복구한다. 전송 리비전과 원본 서버의 데이터 버전은 별도 개념이다. |
| 일관성 | 전체 수신인지 부분 페이지인지, 페이지 완료/버전 조건 | 같은 버전의 데이터가 완성되고 검증된 뒤 교체한다. 부분 실패를 빈 목록으로 해석하지 않고 마지막 정상 상태를 유지한다. |
| 인증과 범위 | 서비스 간 인증, 운영/배송원/고객의 조회 범위 | 고객은 자기 매장, 배송원은 배정 차량/배송지만 서버에서 조회하도록 제한한다. 화면 필터를 권한 검사로 쓰지 않는다. |
| 과부하 | 예상 동시 사용자, GPS/ETA 갱신 주기, 요청/응답 크기 | 타임아웃, 재시도 간격, 제한된 배치 수신과 관측 지표를 실제 계약에 맞춘다. |

현재 `server.js`에는 외부 데이터 수신 API가 없다. 운행/완료 명령은 여전히 기존 실시간 시나리오 ID에 한정되어 있고, 합성 fleet 어댑터는 실서버 ETA/상태 매핑을 제공하지 않는다. 부하 자료가 화면에 보인다는 사실을 실제 운행 데이터 연동 완료로 취급해서는 안 된다. API 주소·인증·응답 예시를 받으면 이 경계에 실제 수신 어댑터와 검증을 연결한다.

## 하루 이력과 저장 용량

현재 데모 사건은 메모리 최근 120건, 스냅샷은 최근 40건이다. 알림은 정차지별 최근 50건을 우선 유지한 다음 전역 최근 1,000건으로 제한된다. 서버 재시작 시 시나리오 이력은 사라진다. 이 구조는 여러 차량의 하루 전체 이력 저장소가 아니다.

앞서 논의한 관제 방향에 따라 실서버에서는 차량을 선택하고 해당 운영 날짜의 실제 사건을 시간순으로 조회해야 한다. 차량별 현재 목적지의 ETA는 최신 상태에서 읽고, 과거 배송지 선택이 현재 ETA를 대체하지 않도록 연결한다. 하루 이력은 별도 저장·조회하며 차량/운영 날짜를 기준으로 페이지 또는 커서로 읽고, 최신 변경은 이어 붙이는 구조가 필요하다. 전체 이력을 실시간 상태에 매번 싣거나 오래된 이력을 삭제해서 화면 부하를 해결하지 않는다. 이 차량 중심 관제 UI와 영구 이력 조회는 아직 구현하지 않았다.

용량 산정에는 `일일 사건 수 × 사건당 저장 바이트 × 보존 일수`에 인덱스, 백업, 복제 비용을 더한다. 사진과 첨부 파일은 별도로 산정한다. 통신량은 `갱신 크기 × 초당 갱신 수 × 수신 연결 수`에 최초 접속/재연결과 지도 타일 비용을 더한다. 실제 사건 발생 빈도와 보존 기간, 동시 고객 수가 아직 없으므로 서버 증설 수치나 최종 저장 용량을 확정하지 않는다.

## 완료 범위

로컬 전송 개선, 대규모 목록 제한, 자동 회귀/부하 도구, 확대 fixture와 주문 OFM 지도 통합을 반영했다. 현재 릴리스 검증은 전체 자동 테스트 142건, 변경 JavaScript 구문 검사, diff 검사, 격리 브라우저와 배포 후 운영 확인을 각각 기록한다. 별도 lint/typecheck 빌드 스크립트는 이 저장소에 없다. 실서버 계약 수신, 입력 검증 어댑터, 차량/매장별 조회 권한 및 구독, 영구 하루 이력과 운영 인프라 부하 검증은 후속 연결 작업이다.
