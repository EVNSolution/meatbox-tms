# 미트박스 TMS 마스터 계획서

범위·결정·진행 상태의 **정본**이다. 2026-10-16 정의 세션에서 시작했다.
원본 요구는 미트박스 업무요구서 2차(수정본) 63항목이며, 아래 괄호 번호는 그 문서의 No다.
다른 계획 문서와 충돌하면 이 문서가 우선한다. 세부 계약은 기준 문서에 두고 여기에는 결론만 둔다.

## 갱신 규칙

- 작업 단위마다 이 문서를 **같은 커밋**에서 갱신한다. 코드만 바꾸고 이 문서를 두지 않는다.
- 상태는 [검증 가이드](verification.md)의 증거 단계만 쓴다. `미착수` → `구현` → `로컬 검증` → `서버 반영` → `업무 확인`. 문서 산출물은 `초안` → `합의`.
- 한 단계의 증거로 다음 단계를 올리지 않는다. 근거 없는 승격은 되돌린다.
- 범위·결정이 바뀌면 "결정 기록"에 날짜와 함께 추가한다. 이전 결정은 지우지 않고 대체했다고 적는다.
- 미트박스 명세·자료가 없는 항목은 `업무 확인`으로 올리지 않는다.

## 범위 경계

우리는 TMS 파트만 만든다. 주문 웹과 고객 앱은 미트박스 것이 있다.

| 우리 몫 | TMS 웹(배차·관제·기준정보·대시보드), 배송원 앱(Android·iOS), 온도 단말(STEGO) 연동, API 서버 |

후속 (트랙 A, 역할):

- **role 없는 계정의 기본값(ops)을 거부로 바꾼다.** 기존 계정을 위한 임시 fail-open이다. 이행 완료 후 `role` 없는 계정이 0건임을 확인하고 바꾼다. 확인 절차는 [운영](operations.md#기사-계정-만들기와-차량-배정)이다.

- 사진·이벤트 결과 조회를 차량에 묶는다. 불변 감사 로그. 운영자 안의 권한 세분화.

후속 후보 (트랙 D):
- 서버는 **현재(`current`) 배송지만** 도착·완료로 받는다. 앱은 `stop_*` 이벤트만 보내므로 현장에서 순서를 건너뛰어 다른 배송지를 먼저 완료하려면 먼저 순서를 바꿔야 한다(건너뛰기 요구가 오면 서버 상태 기계 변경이 필요하다). 오프라인에서 연달아 완료한 건은 큐 순서대로 처리되어 문제가 없다.
- 큐는 앱이 열려 있을 때만 전송한다. 앱을 닫은 채 둘 때의 전송은 백그라운드 작업 단위로 다룬다.
- 앱은 날짜 상태(`GET /state`)·`boot`·`POST commands`를 쓰지 않는다. 하루 전체는 `GET driver/route`, 차량 선택은 `GET driver/vehicles`다. QR 상차 스캔의 "다른 차량 주문" 구분은 없앴다(기사 응답에 다른 차량 주문 ID가 없어 "이 차량 배송 목록에 없는 주문"으로 합쳤다).
