## 1. 목적과 결정 우선순위

운영 업무를 배차 계획, 운행 중 잔여 업무 관제, 운송 자원 관리로 구분한다. 운영 메뉴 이름과 표시 순서는 **배차 관리 → 배송 관제 → 자원 관리**다. 메뉴 순서는 구현 순서를 강제하는 조건이 아니다.

사용자의 이번 요구가 기존 `DESIGN.md`와 `docs/fleet-operations-plan.md`의 충돌하는 내용보다 우선한다. 특히 다음 항목은 이번 요구로 대체된다.

- 주문 관리 / 배송 목록 / 배송 관제라는 기존 메뉴 이름과 순서.
- 선택 차량의 주문만 남기는 배차 지도와 배차 지도 위의 예시 차량 마커.
- 배송지 한 곳을 주 대상으로 삼는 관제와 관제 지도 제거 방침.
- 배송원 뷰어의 진행 배차 / 종료 배차 구분을 근무 이력으로 사용하는 방식.

충돌하지 않는 브랜드, 앱 프레임, 지도 스타일, 접근성, 알림, 경로 편집 보호 규칙은 유지한다. 다른 저장소는 필요한 참조만 읽고 수정하지 않는다.

## 3. 화면별 요구사항

### A. 배차 관리

- **A1. 차량 목록:** 지도에서 차량 마커를 제거하고 좌측 리스트에서 차량을 선택한다. 차량 마커 제거는 배차 관리에 적용하며 고객 및 배송원 지도의 차량 표시를 일괄 삭제하는 요구가 아니다.
- **A2. 전체 주문 지도:** 좌표가 있는 전체 주문을 계속 표시한다. 차량을 선택해도 다른 차량의 주문을 숨기지 않는다. 선택 차량 소속 주문 마커의 그리기 순서를 높이고 선택을 시각적으로 강조한다. 좌표 자체는 이동하지 않는다. 강조는 색상만으로 구분하지 않는다.
- **A3. 완료 예측:** 차량별 고정 출발 시각과 그 차량에 배정된 전체 주문의 완료 예상 시각을 표시한다. 다음 배송지 도착 ETA와 마지막 배송 완료 예상 시각을 구분한다. 고정 출발 시각은 실시간 갱신으로 밀리지 않아야 한다.
- **A4. 주문 시나리오:** 팝업에 총 차량 수, 총 배송지/가구 수, 총 박스 수, 소요 시간, 기사별 박스 수와 가구 수를 표시한다. 평균값과 개별 배정량은 라벨로 구분한다. 전체 소요 시간의 집계 방식이 정해지기 전에는 임의 계산을 넣지 않는다. 기존 명칭 `주문 시나리오`와 80–120% 비교를 유지한다.
- **A5. 권역과 핀배차의 미래 범위:** 차량별 권역 경계와 폴리곤, 내부 배송지/박스 집계, 주변 배송지 확인과 편집을 염두에 둔다. **실제 권역이 오기 전까지 예시 문구만 표시한다. 폴리곤, 가짜 경계, 내부 판정/집계, 드래그 편집, 핀배차 동작 및 임의 배차 알고리즘을 구현하지 않는다.**

### B. 배송 관제

- **B1. 메인 정보:** 차량별 남은 배송지 수, 박스 수, 제공된 예상 소요 시간을 비교한다. 사용자가 단위 결정을 위임하여 배송 ID 1개를 1곳으로 집계한다. 기본은 주문 수신 순서, 선택형 잔여량 정렬에서 미확인 값은 마지막에 둔다. 가구로 별도 환산하지 않는다.
- **B2. 차량 선택:** 차량을 선택하면 해당 차량의 현재 위치와 남은 배송지 마커, 지원배차 진입점을 표시한다. 다른 배송지의 과거 이력을 펼쳐도 선택 차량과 현재 운행 요약이 바뀌지 않는다.
- **B3. 지원배차:** 위치를 기준으로 주변 차량을 확인하고 안정 레벨 상/중/하와 함께 호출/지시하는 흐름이다. 점수 산식, 반경, 적재 가능량, 수락 절차와 재배정 효과를 임의로 확정하지 않는다. 데이터나 명령 연결이 없으면 이유가 있는 대기 상태를 제공하며 실제 지시 성공을 가장하지 않는다.
- **B4. 상세 정보:** 차량 선택 → 우측 카드 → 배송지별 펼침은 핵심 정보(주소/박스/ETA/요청/팁)만 표시한다. 이력·알림 보기로 선택 배송지의 배송 관리에 진입한다. 배송 관리에서 실제 사건과 대상 ID가 일치하는 고객 알림을 시간순 통합하고 전체/처리 이력/고객 알림으로 필터한다. 예정 단계나 다른 대상의 기록을 섞지 않는다. 순서 관리 버튼으로 기존 편집/보류/복원 화면을 열며 저장/취소 보호를 유지한다.
- **B5. 고객 요청:** 냉장고 안, 문 앞 등 배송 요청을 시각적으로 표시한다. 배송원이 남긴 팁, 상품의 냉장/냉동 조건, 고객의 실제 인도 요청을 서로 다른 정보로 취급한다.

### C. 자원 관리

- **C1. 구조:** 기존 배송 목록을 자원 관리로 개편하고 배송원 / 차량 / 배송지 탭을 둔다.
- **C2. 배송원:** 성향, 업무 지표, 메인 권역 등 확인 가능한 정보를 표시한다. 지표 정의와 데이터 출처가 없으면 값이나 평가를 꾸며내지 않는다.
- **C3. 차량과 배송지:** 차량 정보와 배정 관계를 조회하며 배송지에는 기존 배송 팁을 연결한다. 실제 데이터 식별자를 기준으로 연결하고 이름이 같은 자원을 하나로 합치지 않는다.
- **C4. 기존 기능:** 검색과 선택, 배송 팁 등 필요한 기존 조회 기능을 새 구조에 배치한다. 합성 자원 선택이 실시간 V1의 편집/완료 동작으로 연결되지 않도록 한다.

### D. 배송원 뷰어

- **D1. 완료 버튼과 촬영:** 실행 중 사용자가 순서를 확정했다. 도착한 현재 배송지의 배송 완료 버튼 → 증빙 카메라 → 필수 사진 → 고객 요청 확인 → 확인 버튼으로 최종 완료한다. 버튼을 누르거나 사진만 고르는 것으로 서버 배송 완료를 기록하지 않는다.
- **D2. 완료 의미:** 사진 필수와 확인 버튼 최종 완료가 확정됐다. 사진 없이 확정할 수 없다. 취소/재촬영은 완료하지 않으며 현재 배송지/도착 상태 변경 또는 연결 해제 시 기존 증빙을 폐기한다. 완료 표시는 기존 서버 응답을 확인한 뒤 한다. 사진 파일은 브라우저 임시 미리보기이며 업로드/영구 저장은 미연결로 명시한다. 자동 이미지 판독은 범위 밖이다.
- **D3. 요청 아이콘:** 현재 배송지 우측 상단에 분류된 고객 요청 아이콘을 표시하는 것은 선택 요구다. 구현하면 텍스트 설명과 접근성 이름을 제공한다. 자유 텍스트 팁을 근거 없이 고객 요청 분류로 바꾸지 않는다.
- **D4. 금일 배차:** 기존 진행 배차 / 종료 배차 구분을 금일 배차 / 근무 이력으로 바꾼다. 금일 배차에는 오늘의 진행 및 완료 상태를 확인할 수 있어야 한다.
- **D5. 근무 이력:** 사용자가 날짜별 더미 이력을 승인했다. 2026-09-12/14 별도 예시 기록과 날짜 캘린더를 제공하고 현재 snapshot 완료 목록은 재사용하지 않는다. 기록 없는 날짜는 예시 기록 없음으로 표시한다. 실제 날짜별 이력 서비스/영구 저장은 미연결이다.

## 4. 데이터와 기존 디자인 제약

- 차량당 약 70박스, 약 35곳은 규모 검토 가정이며 적재 상한, 배송지 상한 또는 고정 배차량이 아니다. 수신 데이터를 100%로 두고 80–120% 비교를 유지한다. 물량 비율 변경으로 원본 주문과 배정, ETA를 임의 변경하지 않는다.
- 확인되지 않은 시간, 좌표, 박스 수와 업무 지표를 0이나 정상 값으로 대체하지 않는다. 지도는 좌표가 있는 주문을 표시하고 위치 미등록 건수를 별도로 설명한다. 전체 주문 마커를 요구한 화면을 임의 클러스터나 선택 차량 필터로 바꾸지 않는다.
- 기존 도로 위 예시 차량 표시와 실제 차량 위치를 구분한다. 지원배차의 거리/안정도 판단에는 예시 좌표를 실제 수신 위치처럼 사용하지 않는다. 필요한 도로 경로를 구하지 못하면 직선 경로를 대신 그리지 않는다.
- 지도는 현재 채택한 DSV 계열 MapLibre/OFM 자산과 마커를 재사용한다. Command/Control + 휠 확대, 일반 휠 안내 가리개, 접힌 출처 표기를 유지한다. 배송원 마커의 최근 50% 축소와 고객 매장 집 모양, 라임 차량 디자인을 보존한다.
- 고객과 배송원은 공통 폰 크기와 프레임을 유지한다. 시간은 폰 헤더에 두며 뷰어 페이지 헤더 우측에 업무 정보를 다시 넣지 않는다. 기존 고객 뷰어의 매장 선택, 알림 벨, 모두 읽기/삭제와 새 알림 팝업 동작을 보존한다.
- 장식용 가운데점으로 문장이나 서로 다른 항목을 연결하지 않는다. `송파·강남` 같은 고유한 지역 표기는 허용한다. 아이콘은 정렬된 SVG와 충분한 클릭 영역을 사용한다.
- 운영 사건에는 실제 발생한 업무 사실을 기록한다. 수동 상태 선택, 시나리오 조작 같은 개발/시연 조작 문구를 사건으로 노출하지 않는다. 기존 시나리오 전환과 고객 알림의 연동은 유지한다.
- 기존 경로 편집의 저장/취소, 오래된 상태 저장 거부, 현재/완료 배송지 보호와 인증 경계를 보존한다. `workspaces/jiin-ui/`와 `workspaces/sanghyun-scenario/` 및 보존 원본 검증 파일을 수정하지 않는다.
- 실제 서버 연동, 영구 이력, 사진 저장이 없으면 연결 완료로 보고하지 않는다. 최근 기록 제한을 하루 전체 이력으로 표현하지 않는다.

## 5. 결정이 필요한 업무 기준과 작업 처리

| 미정 사항 | 확인할 내용 | 그동안 진행 가능한 작업 |
|---|---|---|
| 사진 저장 | 버튼→필수 사진→확인 완료는 확정. 업로드/영구 보관 계약은 없음 | 로컬 필수 사진/재촬영/취소/연결 해제 보호와 서버 완료 응답 검증 |
| 지원배차 | 안정 레벨 정의, 위치 출처, 대상 조건, 호출/수락/재배정 단계 | 차량 목록, 잔여량 표시, 지도, 지원배차 대기 상태 |
| 시간 지표 | 마지막 도착과 인도 완료의 구분, 하차 시간, 팝업 총 소요 시간 집계 | 시각과 기간의 구분, 제공값 표시, 미확인 상태 |
| 수량과 정렬 | 배송 ID 기준 배송지/박스, 주문 수신 순서 기본은 확정 | 선택형 잔여량 정렬, 결측은 마지막, 원본 불변 |
| 자원/이력/요청 데이터 | 배송원 지표/고객 요청/실제 근무 이력 계약은 없음. 별도 더미 이력 승인 | 자원 탭, 날짜별 예시 이력, 데이터 경계와 빈 상태 |

미정인 업무 규칙을 확정 요구로 바꾸지 않는다. 구현에 꼭 필요한 질문은 초기에 묶어서 전달하고 의존하지 않는 작업을 계속한다. 답이 없다는 이유로 완료 시점, 안정도 산식이나 실데이터 계약을 임의 확정하지 않는다. UI 배치, 파일 분리 등 되돌릴 수 있는 구현 선택은 기존 패턴에 맞춰 직접 처리한다.

## 6. 실행 순서

1. 작업 트리와 관련 코드, 기존 디자인/테스트 문서를 확인한다. 이 문서의 근거와 요구 ID를 검토하고 필요한 업무 질문을 기록한다. 구현 전에 화면 구조, 데이터가 없는 경우의 동작, 확인 기준을 문서에 확정 범위와 미정 범위로 나누어 남긴다.
2. 충돌하는 `DESIGN.md`와 기존 운영 계획의 관련 설명을 최신 요구로 맞춘다. 공통 메뉴, 차량 선택과 배송지 선택의 관계를 정리한다.
3. 배차 관리의 좌측 차량 목록과 전체 주문 강조, 확인 가능한 지표와 주문 시나리오 정보를 구현한다. 권역은 예시 문구만 둔다.
4. 배송 관제의 차량별 잔여 업무 요약과 정렬, 지도와 우측 상세, 사건/알림 조회를 구현한다. 지원배차는 확보된 데이터와 확정된 업무 규칙 범위에서 동작시킨다.
5. 자원 관리 탭과 상세를 구현하고 기존 배송 팁과 조회 기능을 연결한다.
6. 배송원 금일 배차와 근무 이력, 요청사항 표시를 구현한다. 사진 필수/확인 완료의 확정 흐름과 별도 더미 근무 이력을 연결한다.
7. 관련 회귀 검사와 화면 확인을 수행하고 발견한 문제를 수정한다. 구현 완료, 데이터 대기, 업무 결정 대기를 구분해 이 문서와 관련 운영 문서에 결과를 남긴다.

독립적인 작업이 충분하면 Codex native subagent에 파일 소유 범위를 나누어 맡길 수 있다. 공유 메뉴/상태 파일의 동시 편집은 조정하고 리더가 통합과 최종 확인을 책임진다. 이 계획을 실행한다는 이유만으로 별도 런타임 워크플로를 시작할 필요는 없다.

검증은 변경한 동작에 대한 집중 테스트부터 수행한다. 현재 저장소의 기본 검사는 `npm test`이며 수정한 JavaScript의 문법 검사와 `git diff --check`도 수행한다. 별도 lint/typecheck 스크립트가 있는지는 실행 시 확인하고 없는 도구를 있다고 가정하지 않는다. 전송/대량 렌더링을 변경했다면 기존 용량 검사도 관련 범위에서 수행한다.

브라우저에서는 모든 운영 메뉴와 배송원 탭, 고객 회귀 화면을 직접 확인한다. 전체 주문 표시에는 실제 운영 데이터와 섞이지 않는 격리된 대량 좌표 테스트 자료를 사용할 수 있다. 현재 수량에서 선택/정렬/갱신의 반응성과 좁은 화면의 넘침을 확인하며, 이 결과를 실제 운영 트래픽 검증으로 보고하지 않는다.

실제 서버 데이터나 필요한 업무 결정이 없으면 해당 기능은 미완료/대기로 기록한다. 동작하는 나머지 범위의 구현과 검증은 끝까지 수행하되 전체가 완료됐다고 보고하지 않는다. 배포는 별도 요청 범위이며 이 계획의 기본 완료점은 로컬 구현, 검증과 문서 갱신이다.

### 데이터 근거

- 차량 `id/plate/driver/region/live/planned`와 배송지 `id/vehicleId/status/boxes`만으로 배정과 잔여 배송지/박스를 계산한다. 보류 배송지는 별도 건수로 표시하고 남은 업무에서 숨기지 않는다. 가구 수로 환산하지 않는다.

- 사건의 원본 `ts`와 명시된 ID를 보존한다. 현재 일반 사건은 대상 ID가 없어 메시지의 이름을 파싱해 배송지에 연결하지 않는다. 알림의 `stopId`는 존재한다. 최근 사건/알림 보존 범위를 하루 전체 이력으로 표현하지 않는다.

1. 이 문서와 DESIGN 및 충돌 문서를 저장한다.
