# 수동 시나리오 전환 계획

## 목표

합본 데모의 시간 기반 자동 진행을 제거하고, 검토자가 필요한 장면을 즉시 선택하는 수동 시나리오로 바꾼다. 주문과 배송은 각각 세 개의 짧은 버튼으로 구분한다. 버튼을 누르면 선택한 실시간 배송지의 상태를 한 번 계산해 모든 연결에 반영하며, 다음 시간이나 사건을 기다리지 않는다.

수동 전환 자체는 로컬에서 먼저 검토했으며, 현재 다차량·지도 통합 릴리스는 별도 SHA로 배포하고 인증된 운영 화면까지 확인한다. 운영 계정 내용은 변경하지 않는다.

## 시나리오 계약

| 그룹 | 화면 라벨 | 명령 값 | 결과 |
|---|---|---|---|
| 주문 관련 | 접수 완료 | `received` | 주문 접수가 끝난 출고 준비 시작 상태 |
| 주문 관련 | 피킹 중 | `picking` | 피킹 진행 상태 |
| 주문 관련 | 출고 준비 | `ready` | 라벨과 상차 준비가 끝난 출발 전 상태 |
| 배송 관련 | 배송 중 | `shipping` | 선택 배송을 포함한 V1 배송 진행 상태 |
| 배송 관련 | 배송지 도착 | `arrived` | 선택한 V1 배송지의 실제 도착 상태 |
| 배송 관련 | 배송 완료 | `completed` | 선택한 V1 배송지를 완료하고 다음 실시간 목적지를 정한 상태 |

게이트웨이 명령은 다음 한 종류를 사용한다.

```js
{ type: "set_scenario", scenario, stopId }
```

- `scenario`는 표의 여섯 값만 허용한다.
- `stopId`는 현재 선택한 실시간 V1 배송지 `S1`부터 `S8`까지만 허용한다.
- 합성 배송지 `V2-S1`부터 `V130-S35`까지는 현재 데이터가 화면 밀도 검토용임을 표시하고 시나리오 버튼을 비활성화한다.
- 사용자는 여섯 프리셋을 임의 순서로 선택할 수 있다. 이전 프리셋에서 시간이 흐르거나 중간 이벤트가 발생하기를 기다리지 않는다.
- 유효한 다른 프리셋을 한 번 선택하면 서버 계산과 상태 전파를 한 번만 실행한다. 같은 프리셋과 배송지를 다시 선택하면 상태 계산과 전파를 하지 않는다. 자동 재생, 연속 애니메이션과 반복 `tick`을 사용하지 않는다.
- 프리셋 전환은 작성된 배송팁과 운영자 수동 안내를 삭제하지 않는다.
- 프리셋 선택과 배송 순서 변경은 이미 설정된 고객 약속 시간대와 운영 정확 ETA 기준을 초기화하지 않는다. `arrived`와 `completed`는 선택 배송의 고정 실제 도착 시각을 운영 정확 시각으로 제공한다. 아직 고객 약속이 없는 배송만 해당 도착 시각을 기준으로 최초 시간대를 만든다. 고객 약속과 정확 ETA 기준을 전체 초기화하는 동작은 명시적 `reset`뿐이다.

스냅샷 최상위에는 현재 선택을 `scenarioPreset`과 `scenarioStopId`로 제공한다. `scenarioPreset`은 여섯 값 또는 `null`, `scenarioStopId`는 `S1`부터 `S8` 또는 `null`이다. `reset`은 `received`와 `S1`으로 초기화한다. 배송 순서 변경, CAS 저장이나 보류처럼 현재 프리셋의 의미를 깨는 다른 명령 뒤에는 두 값을 `null`로 돌릴 수 있으며, UI는 임의의 프리셋을 추정하지 않는다.

## 타이머와 기존 기능 경계

- 서버의 500ms 시뮬레이션 진행 타이머를 제거한다.
- 현재 `OperatingSimulation`에서는 `arrive_stop`이 도착까지 `tick(true)`를 반복하지 않고 `arrived`를 한 번 적용한다. 배송원 화면과 `arrive_stop`, `complete_stop` 명령 호환성은 유지한다. 보존 원본과 함께 시험하는 일반 시뮬레이션용 최대 10,000회 안전 제한은 폴백으로 남지만 합본 운영 경로에서 실행되지 않는다.
- 시나리오 가이드의 자동 주행, 자동 하차 완료, 배속, 사고와 정차 지연 버튼을 제거한다.
- WebSocket의 이전 `advance`, `place_order`, `speed`, `traffic`, `dwell` 명령은 차단한다. 배송원 화면의 도착과 완료 조작은 기존 `arrive_stop`, `complete_stop` 명령을 유지하되 각각 `arrived`, `completed` 프리셋의 단일 전환으로 처리한다.
- 인증 만료 확인, 속도 제한 정리와 브라우저 WebSocket 재연결에 필요한 타이머는 유지한다.
- 같은 Origin, 인증 세션, 사용자 단위 명령 제한, 고객 알림 보존 상한, 배송 순서 CAS와 기존 고객 ETA 앞뒤 30분 정책은 유지한다.
- `workspaces/jiin-ui/`, `workspaces/sanghyun-scenario/`와 지인님의 60016 디자인 가이드는 수정하지 않는다.
- `/scenario/` 아래 화면 요청은 대응하는 합본 화면으로 이동한다. 원본 검증과 합본 의존성에 필요한 route data와 공용 정적 자산은 계속 제공한다.

## 화면 구성

전역 시연 가이드는 긴 단계 설명서 대신 `주문 관련`과 `배송 관련` 두 그룹을 보여 준다. 주문 관련은 `접수 완료`, `피킹 중`, `출고 준비`, 배송 관련은 `배송 중`, `배송지 도착`, `배송 완료` 버튼과 현재 선택 상태만 제공한다. 화면에는 명령명, 파일명, 서버 계산 방식 같은 개발 구조를 설명하지 않는다.

주문 관리 본문에서 배송량 편집기를 제거한다. 지도 한쪽 모서리에 `주문 시나리오` 버튼을 두고, 열리는 작은 팝업에서 수신 데이터의 전체 박스 합계를 기준으로 다음 브라우저 범위 미리보기만 조절한다.

| 설정 | 범위 | 의미 |
|---|---:|---|
| 목표 물량 | 80–120% | 수신한 전체 배송 박스 합계를 100%로 둔 평가 준비용 미리보기 |

기본값과 초기화 값은 100%다. 목표 물량은 브라우저 안의 요약만 바꾸며 원본 스냅샷, 개별 주문 박스 수, 지도 주문 마커, 차량·배송지 수, 배송 상태, 운영 정확 ETA, 고객 약속 시간대, 알림과 배차 순서를 변경하지 않는다. 기준값 누락은 `미확인`, 명시적인 빈 배열이나 박스 합계 0은 0으로 취급한다. 팝업에도 자동 진행이나 연속 애니메이션 타이머를 두지 않는다. 실제 증감 배분 방식, 배차 알고리즘과 성능 평가 지표는 아직 확정하지 않으며 새 평가 프레임워크를 만들지 않는다.

## 구현 순서

1. 게이트웨이에 인증된 `set_scenario` 검증, V1 전용 단일 계산 경로와 현재 프리셋 메타데이터를 추가한다.
2. 서버 자동 진행 타이머와 반복 도착 경로를 제거하고, 운영용 인증·연결 타이머가 남아 있는지 확인한다.
3. 전역 가이드를 주문 세 버튼과 배송 세 버튼의 수동 선택 UI로 교체한다.
4. 주문 관리 본문 편집기를 지도 모서리의 `주문 시나리오` 팝업으로 옮기고 목표 물량 비율을 로컬 미리보기 상태로 분리한다.
5. 회귀 테스트와 320px, 390px, 1280px 브라우저 검증을 실행한다.

완료 기준은 [수동 시나리오 테스트 명세](manual-scenarios-test-spec.md)에 정의한다.

## 다음 배송지 선택 (2026-09-15)

사용자는 자동 진행 요청을 ‘다음으로 넘기는 버튼’으로 정정했다. 리모컨에 `다음 배송지`를 추가하며 현재 V1 배차 순서의 다음 항목을 해당 뷰어에서 선택한다. 선택 후 기존 여섯 프리셋을 사용한다. 선택 이동만으로 배송 상태나 알림을 생성하지 않는다. 마지막 항목은 `마지막 배송지`로 비활성화하고, 연결 대기·시나리오 응답 대기·합성 차량에서는 이동을 막는다. 고객 뷰어의 매장과 지도, 배송원 지도 상세, 운영 선택 대상과 뷰어 이동 링크를 같은 ID로 맞춘다. 자동 재생 타이머와 서버 명령은 추가하지 않는다.
